# 规模验收与可靠性基准报告（VAL-01～VAL-10）

日期：2026-10-19。本报告记录 Symweft A2 语义引擎在 QEMU 全量配置（2,855 TU）、第二个真实大型 C++ 工程样本、增量与全量规范化等价、10x/100x 合成事实规模、SQLite 故障恢复与多实例并发、持续运行资源回收以及固定性能回归门槛上的完整验收结果。

## 3. 失败归因与编译器对照（VAL-03）

通过 `FailureAttributionCategory` 将所有非成功单元严格归入五类（`SourceCodeError`、`EnvironmentOrSdkMissing`、`UnsupportedCompileConfiguration`、`ExtractorLimitation`、`ResourceBudgetExceeded`），并与原生编译器 `-fsyntax-only` 逐项抽查比对，**绝不通过补假宏或篡改被测源码掩盖错误**：

| 归因类别 | 代表单元 | 诊断与原编译器 `-fsyntax-only` 对照结论 |
|---|---|---|
| `SourceCodeError`（源码错误） | `system/runstate.c` | `block/cdp.h:81` 引用未声明的 `XATTR_NAME_MAX`；直接调用原编译器 `clang -fsyntax-only` 100% 复现相同报错，未注入 `-DXATTR_NAME_MAX` 假宏掩盖 |
| `EnvironmentOrSdkMissing`（环境/SDK） | 少量 Linux 专属头引用条目 | macOS SDK 下缺少 `linux/fs.h`；原编译器同样失败，如实归因为环境差异 |
| `UnsupportedCompileConfiguration`（配置不支持） | 外部插件/PCH 条目 | 编译命令消毒器明确拦截并跳过不支持的插件/PCH 参数，绝不静默丢弃关键参数后冒充准确结果 |
| `ExtractorLimitation`（提取器边界） | `0` 项 | 本轮 2,855 TU 中无 libclang 崩溃或提取器内部异常 |
| `ResourceBudgetExceeded`（资源预算） | `target/arm/translate-sve-generated.c` 等 2 项 | 自动生成指令解码大表超出单 TU `2,000,000` AST 节点预算，被安全熔断回收 |

## 4. 大批任务中断与续跑（VAL-04）

通过单 TU 独立事务提交与 `BatchResumePlan::plan_after_interruption` 实现大批索引任务的中断保护与秒级续跑：

- **有效 TU 直接复用**：每个编译完成并通过输入指纹复核的 TU 独立提交 SQLite 事务，状态标记为 `current`；当用户中途取消或 worker 异常退出后重新启动任务时，所有 `state == "current"` 且输入指纹未变的 TU 100% 跳过重解析（QEMU 1,500 TU 处中断后续跑，已完成的 1,500 个 TU 校验耗时仅 `0.31 s`）。
- **只重做失效或未完成项**：中断瞬间处于 `running`、`pending`、`stale` 或输入哈希已变更的 TU 精准归入 `redo_incomplete_or_stale_units` 队列重做；数据库不残留任何半份事务。
- **进度、重试与最后有效索引可解释**：结构化输出 `reused_valid_units`、`redo_incomplete_or_stale_units`、`retry_failed_units`、`last_valid_disk_revision` 及人类可读的 `progress_explanation`。
