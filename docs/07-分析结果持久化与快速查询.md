## 1. 决策与优先级

最新增量：已实现原生文件事件消费、TU 自动重建、持久查询连接和有界输入指纹缓存；当前 watcher 为协作式维护，非完整文件系统原子快照，详见 [实现、边界与对照](11-实时语义更新与查询优化.md)。本文件中的完整 generation/连续编辑 overlay 仍是目标架构。

采用 **本地 SQLite 持久化索引 + 按文件/作用域保存的紧凑事实块 + 有预算的内存快照 + 未保存编辑 overlay**。

用户要求的两个核心行为：

1. 已分析且未变化的文件，在重启后打开时可以直接读取大纲和关系，不重新分析整个项目，也不强制先重建当前文件语法树。
2. 内容变化先更新活动文档的内存事实，再异步提交已保存内容的持久化版本；更新的范围限于受影响的分析单元，不重写整个数据库。

**A1 语法事实持久化提前到下一实施步骤，不等待完整 A2 语义分析完成。** 先实现退出/重启后的复用，再扩展准确的语义关系、工作空间与跨项目查询。

## 2. 三层数据与寿命

| 层 | 保存内容 | 读取与更新方式 | 寿命 |
|---|---|---|---|
| 磁盘基线 | 文件身份/内容指纹、分析输入键、定义与作用域、调用点、语义关系与证据、依赖、版本指针 | SQLite 索引定位；事实块按需解码；事务发布新版本 | 跨进程保留，可重建 |
| 热快照 | 当前文件的大纲、范围/作用域索引、已查询的邻接页；少量源码与可选语法树 | 内存直接查询；按内存配额淘汰 | 活动会话 |
| 编辑 overlay | 未保存内容的修订、替换后的事实、被遮蔽的旧关系、受影响依赖状态 | 先覆盖基线，再查询；新修订原子替换 | 文档编辑期间 |

完整 AST 不作为首版通用持久化格式。语法树/编译器对象有版本和平台约束，体积与内存开销也不同于紧凑事实。读取持久化事实不需要 AST；第一次编辑需要 AST 时再从已校验的源码建立，并缓存后续增量状态。

已将事实改为共享 `Arc<Facts>`、Tree 改为可选。读取已校验快照使用 `Engine.restore`，无 AST；第一次编辑再建立树，后续增量解析。尚未保存的编辑只修改活动内存快照。

用户手工注释、规则、阅读路径和架构定义不是可丢弃索引，保存在独立的用户资产存储中；清理分析缓存不删除这些内容。

## 3. 磁盘布局与数据组织

默认一个活动工作空间对应一个本地分析库，多项目通过 project_id 区分，不为每个源码文件建立一个 SQLite 数据库。

示意路径：

- macOS：~/Library/Caches/Symweft/workspaces/<workspace-id>/analysis.sqlite3
- Linux：$XDG_CACHE_HOME/symweft/workspaces/<workspace-id>/analysis.sqlite3；未设置时使用 ~/.cache。
- Windows：平台本地缓存目录下的 Symweft/workspaces/<workspace-id>/analysis.sqlite3，不放入漫游配置。

工作空间 ID 由本机注册信息维护，关联规范化根目录与项目身份；不只用 basename。移动/重命名项目需要重新绑定或校验，不能把不同路径的同名项目合并。磁盘可清理、只读或不可用时回退到内存分析，不阻止源码阅读。

同一事务维护两类访问结构：

**文件视图**：按版本、文件、块类型、作用域定位事实块。大纲通常一次读取；当前函数调用点单独读取，避免打开文件时解码全库关系。事实块使用带版本、长度上限与校验的紧凑编码，首版候选为 Protobuf；小块先不压缩，大块是否压缩由磁盘/CPU 基准决定。SQL 结构不依赖编码器的内存布局。

**全局查询索引**：符号、引用、边、证据与依赖使用可索引字段。查询按 ID 进行，名称用于展示和搜索，不用字符串同名匹配代替语义绑定。初期仅持久化 A1，未解析调用点存入文件事实块，不伪造 A2 调用边。

两者由同一批分析结果生成，不进行两次独立分析；发布指针在两者准备完整后更新。优先保证常用读取路径，控制冗余字段，实际测量事实块和全局索引的总空间。

## 4. 记录身份、缓存键与所有权

最少包含：

| 记录 | 关键字段 | 用途 |
|---|---|---|
| SourceFile | project_id、相对 URI、file_id | 按路径直接定位，不混淆同名文件 |
| BuildVariant | project_id、variant_key | 分开宏、features、classpath、目标等配置 |
| AnalysisUnit | provider 的 owner_key、variant、phase | 确定哪些事实由一次分析产出 |
| AnalysisVersion | unit、输入键、分析器键、generation | 校验复用条件和发布版本 |
| UnitInput | version、file_id、content_hash、role | 校验源码并反查受影响分析单元 |
| FactChunk | version、file、作用域、块类型、编码、payload | 快速读取大纲和函数调用点 |
| Symbol | 内部整数 ID、带域的逻辑键、variant、名称/种类 | 提供紧凑的关系端点 |
| Relation | owner_version、source、target/unknown、kind、位置、证据 | 双向关系查询与解释 |

语法缓存输入键主要由源码字节、grammar/提取器版本、规则与格式版本组成；语义缓存还必须包含依赖摘要、语言环境、工具链与构建变体。

mtime 与 size 仅作快速筛选，不能单独证明内容相同。打开文件本来就需要读取文本，可在同一读取流程计算内容指纹。输入键以规范化、有域区分的编码构造，不能用无分隔字符串拼接。

文件字节偏移不是稳定语义 ID。局部 ID 必须与所属版本关联；嵌套调用可共享起始偏移，调用点不能仅用 start_byte 唯一标识。

### 分析单元不总等于文件

Python 的语法单元可以是单文件；C/C++ 语义可能由 TU 与编译变体拥有，并对头文件产生贡献；Rust 提供器也可能按 crate/module 组织输出。因此持久化按 owner unit 替换其产出。重新分析一个 TU，不能删除其他 TU 对相同头文件的有效语义贡献。

文件视图通过 file_id + variant + phase 找到适用的单元与版本，不把不同构建变体的语义混为一个结果。

## 5. 打开文件时的读取路径

~~~text
选择文件
  ├─ 读取源码并立即呈现文本；同次读取计算内容指纹
  └─ 定位工作空间库 → 文件/分析单元 → 当前版本
        ├─ A1 输入键匹配：直接读取大纲/作用域事实块
        │      └─ 光标所在函数 → 读取调用点块 → 内存查询
        ├─ A1 不匹配或缺失：按需语法分析，发布新快照
        └─ A2：检查环境与依赖验证状态
               ├─ 已验证：提供当前语义关系
               └─ 未验证：旧结果标记 stale，安排依赖校验/增量分析
~~~

读取不能依赖先启动全部语言服务。只有文件事实还不足以回答的问题，才按需请求语义提供器或后台补齐。

重启后，当前文件没变，但头文件、依赖、JAR 或锁文件可能在应用关闭期间发生变化。**本文件 hash 命中不能直接证明 A2 仍有效。** 启动时后台对账，活动查询优先校验相关依赖；未验证的旧语义保留可浏览状态，但不得冒充当前精确结果。A1 可以在其自身输入键匹配后先独立发布。

## 6. 查询如何保持局部读取

- 文件大纲：通过 analysis unit 的 head 与事实块主键读取，不扫描所有 symbol/edge。
- 当前函数：在已解码快照中以范围/作用域索引定位；移动光标不重解析、不全库查找。
- 函数调用谁：通过 source_symbol_id + relation_kind 的索引读取邻居。
- 谁调用函数：通过 target_symbol_id + relation_kind 的反向索引读取邻居。
- 文件变化影响谁：通过 UnitInput 的 file_id 反查当前仍引用该输入的分析单元，再由语义摘要决定是否传播。
- 图谱展开：固定快照、按页读取，并限制深度/节点/边/时间；使用游标，不随着页数增加使用大 OFFSET。

索引是否实际生效必须检查查询计划，随后在真实数据上测量，而不是仅凭建表语句推断毫秒数。SQLite 的复合索引按查询条件顺序设计，避免维护冗余的前缀索引。[查询规划依据](https://www.sqlite.org/queryplanner.html)

DDL 草案见 [analysis-storage-schema.sql](analysis-storage-schema.sql)。它展示文件事实块、分析所有权、双向关系和版本发布结构；不是已接入产品的数据库迁移。

## 7. 快速更新与原子发布

### 编辑尚未保存

活动文档修订 R → 增量解析 → 内存发布 R+1 → UI 与关系查询使用新 overlay。旧事实按分析所有权遮蔽，不能简单把新边追加到旧边上，否则删除调用后仍会出现幽灵关系。

未保存 overlay 不直接覆盖磁盘基线。自动恢复草稿如需落盘，使用独立的恢复日志与修订标识，不能将其当作已保存源码的事实。

### 已保存文件或外部变更

1. 合并变更事件，确定最新 desired input key 与工作空间/单元 epoch。
2. 分析受影响单元，尽早发布可用的内存结果。
3. 后台单写队列合并同一单元的旧任务，只保留需要发布的最新版本；队列按字节/任务数限额，有背压，不无限堆积。
4. 短事务写入新版本、事实块、关系与输入清单；验证结果仍对应最新输入。
5. 同一事务更新 head 与 generation/历史区间，使读者从完整旧版本切到完整新版本。
6. 过期结果不推进 head；写入失败时继续使用内存快照并报告“尚未持久化”，不谎称磁盘提交成功。

新分析版本只替换受影响 unit 的产出；其他文件不复制一遍。首版允许按单文件/分析单元替换事实。进一步优化为作用域块复用时，使用相对位置与独立锚点，避免在文件前面插入一行就重写后面所有函数的相同事实。

保存源码与提交索引不是同一文件系统事务，因此始终以源码内容指纹校验结果，不能依赖“上次保存成功”推出索引必然同步。

## 8. SQLite 并发、快照与资源预算

SQLite 使用 WAL，允许读者与写者并行，但单库只有一个写者，因此安排一个写队列和少量读取连接。读事务要短，长图遍历不一直持有数据库事务；WAL 的 checkpoint 也必须纳入后台调度。[WAL 依据](https://www.sqlite.org/wal.html)

每次 UI 请求读取一个完整已提交版本。短事务内的多次查询共享数据库视图；分多页的长查询则固定逻辑 generation，以 publication 区间选取版本。旧版本通过 lease 保留到查询结束，不能每页偷偷读取新的 head。单次事务隔离与跨请求快照是两种机制。[事务隔离依据](https://www.sqlite.org/isolation.html)

首版资源策略：

- SQLite 页缓存计入总内存预算，按连接累加计算；从小预算开始，不默认复制整个图到内存。
- 当前文件事实块与邻接页有独立、合计受限的缓存，文件关闭可回收；不将“缓存命中”强制转换为 AST 常驻。
- 写批次有大小与工作时间上限；批量初次索引不能形成长时间阻塞交互的巨大事务。
- WAL 大小、checkpoint 延迟、读事务持续时间均可观测。空闲时做回收，不每次编辑 VACUUM；大规模删除后再安排空间整理。
- 数据库位于本地缓存盘，源码可以位于其他位置；不把 WAL 库直接放到网络共享目录。
- 历史按配额与 lease 回收。旧版本删除前先释放引用，不能把已被快照引用的块当作垃圾。
- 首版一个工作空间库，后续只有真实测量表明单写队列或体积成为瓶颈时，才按项目分片；跨库发布使用 SnapshotSet manifest，不假设跨库原子提交。

派生分析缓存可评估 WAL + synchronous=NORMAL，接受断电/系统故障后最近一批缓存需要重建；用户资产使用单独的持久性策略，不沿用这个取舍。[同步策略依据](https://www.sqlite.org/pragma.html#pragma_synchronous)

实现时固定、校验实际 SQLite 版本，使用含 WAL-reset 修复的版本（官方列出 3.51.3 及以后或指定回移版本），不默认所有平台系统库都具备相同修复。写入与 checkpoint 的并发路径纳入故障测试。[官方版本说明](https://www.sqlite.org/wal.html#walreset)

## 9. 实施阶段与验收

**P1：持久化 A1 与重启复用。** 增加独立存储模块/线程、版本化编码、文件输入键、按需加载、FactSnapshot/SyntaxState 拆分；缓存命中无需解析。验证不同路径同名文件、应用关闭期间修改、解析器升级、损坏或不可写缓存等情况。

**P2：编辑 overlay 与异步提交。** 验证未保存内容不污染基线、迟到任务不能回退 head、批次失败不暴露一半结果；连续输入下队列可合并并有上限。先完成后台调度，不能把同步 SQLite 写入加入当前顺序请求热路径。

**P3：A2 关系持久化。** 加入准确的符号/出入边、依赖输入、变体和证据；验证 TU/头文件共享所有权、公开摘要变化的传播、旧边遮蔽与删除、跨项目快照一致性。

必须分别测量：

1. 退出后重新启动、未变化文件打开：读盘/指纹、元数据定位、事实块读取/解码、关系首屏分别计时，确认 parse_count=0。
2. 相同会话热打开和光标查询：命中快照与邻接缓存，不随仓库大小做线性工作。
3. 修改一个函数：内存可见延迟、分析耗时、写入排队/事务耗时、实际写入字节与失效单元数。
4. 百万/千万事实样本：冷页/热页分别测试查询、写入、磁盘体积、RSS、WAL 增长和回收。
5. 切分支/批量删除/配置变化/崩溃恢复：不能将旧语义标成 current，不能丢失用户资产。

当前的 400 函数语法微基准没有覆盖上述磁盘路径，本轮不把它当作持久化性能证据。具体延迟目标需要在固定机器与真实数据上建立基线后确定。

### 本轮设计验证

DDL 已在内存 SQLite 中执行验证。示例数据上的 EXPLAIN QUERY PLAN 确认：大纲按单元唯一索引与事实块主键读取，出入调用分别使用 relation_out/relation_in，依赖反查使用 unit_input_by_file，无全表扫描。已验证新 head 切换后只返回新关系、固定 generation 仍能读取旧关系，以及单元/版本所有权约束失败时事务整体回滚。

以上草案验证与本轮运行时基准分别记账，不代替未来语义层的大规模并发测试。

## 10. 当前 A1 实现与目标架构的映射

- 一个工作空间一个 SQLite WAL 库，`snapshots` 按相对路径主键保存源码 BLAKE3、payload 校验、源码字节数和完整文件事实块。格式为 `SWF1` + 固定版本 bincode 2 编码；分析器键覆盖 grammar/提取器/格式版本。当前不是 Protobuf，也没有按作用域拆块。
- `definitions`、`lexical_calls`、`dependencies` 为可查询的二级索引；`usage` 保存独立用户关注。同名调用计数仅为 `syntax_proxy`，不生成已绑定关系边。
- 替换同一文件时，在一个事务内更新快照并删除/重建该文件二级行，删除调用不会残留旧计数。全量命令在成功遍历后删除不存在的文件及相关记录；遍历失败不按不完整清单删库。
- 交互使用专用存储线程；队列最多 32 条命令，事实写入载荷最多 16 MiB，合并最多 16 个连续写入。返回 `queued` 仅表示入队，`index.flush` 才确认前序写入并 checkpoint；错误可由状态读取。NORMAL 模式适合可重建缓存，断电可能丢失近期提交；不用于保存不可丢失的用户资产。
- 默认路径为平台缓存根下 `Symweft/<canonical-root-hash>/a1-v2/index.sqlite3`，测试可用 `SYMWEFT_CACHE_DIR` 指定根。当前移动目录后重新建立身份；尚无重绑定 UI。
- 事实热池按字节估算、最多 4,096 项，独立于引擎活动源码/AST。自动预算、SQLite 页缓存随压力调整；引擎当前仍保留自己的 8 文档/64 MiB 估算上限。关闭附加缓存不代表关闭当前文档分析或限制整个 RSS。
- 本轮实现自定义 append pack 和 SQLite+segment 混合后端用于对比；生产打开链路仍选 SQLite。实验格式的 GC、跨平台崩溃注入、多进程写锁与迁移未完成。
- 尚无文件监听/保存接口；磁盘变化在再次打开和显式全量命令时校验。离线修改不会误命中 A1；未来 A2 仍必须校验依赖与环境，不能仅看当前文件 hash。
