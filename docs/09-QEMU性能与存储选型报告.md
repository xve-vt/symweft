# QEMU 性能、持久化选型与热缓存报告

日期：2026-10-18。对应实现：Symweft 0.1.0，A1 v2。原始数据见 [JSON](09-QEMU基准原始数据.json)，实现入口为 `crates/symweft-index` 与 `symweft-core index`。

后续进展：C/C++ 首版 A2 的真实编译配置、紧凑关系索引和 QEMU 30 TU 子集结果见 [语义报告](10-C-Cpp语义闭环与QEMU验证.md)。本报告的数字仍属于此前 A1 语料和实现，不代表 A2 性能。

## 1. 结论与决策

**当前采用 SQLite WAL + 自定义版本化二进制文件事实块 + 有预算的内存事实缓存。** SQLite 满足本轮 QEMU 的文件恢复与更新需求，没有证据表明需要立即替换整个数据库。这里的判断仅适用于已测 A1 规模，不能外推为千万/亿级语义边的证明。

已实际实现并测试四种存储形态：SQLite 仅快照、SQLite 快照加二级索引、append pack、SQLite 元数据加外部分段事实块。纯 pack 读取最快，但不提供完整二级查询；完整混合方案在本次构建中更慢，体积只比完整 SQLite 小约 8%，热读尾延迟差距很小。暂不承担它的回收、锁、跨平台崩溃恢复与迁移成本，保留实验实现和可复现基准。

本轮代码已落地持久化、免 AST 恢复、独立写线程、事务替换、有界热池、动态压力控制、手动设置、受限预读、双维热度 API 与 JSON/CSV 导出。当前尚无完整语义解析、跨项目图谱和千万级事实验证。

| QEMU | VERSION 11.1.1；commit `2df3db357e2d59b7e56c8fa9b97cd035e67d473b` |
| 支持的源文件 | 6,723：C 3,688、头文件 2,551、Python 416、Rust 63、C++ 5 |
| 源码体积 | 65,000,505 字节，约 61.99 MiB；2,031,648 编辑器行 |
| 构建信息 | 无 compile_commands.json；未配置/编译 QEMU，未下载子模块 |
| 页缓存 | 不执行 purge；OS 页缓存可能已热，应用连接按轮重开 |

这里只统计当前语言扩展名，不包含 QEMU 所有脚本、生成器、构建描述和数据文件。头文件暂按 C grammar。Java 由现有多语言测试验证，QEMU 样本中没有 Java 源文件，不能用此报告评价 Java 大仓库性能。

统一先生成一次 A1 事实与相同 bincode payload，再导入各后端，避免重新解析差异污染存储对比。随机读采用固定请求序列，每轮 1,500 次快照读取和 500 次源码校验读取，三轮轮换后端次序。不是物理冷盘测试，也不是跨机器统计置信区间。

全量路径另测真实生产 CLI，包含读源码、解析、提取、编码、二级索引事务和 checkpoint。`wall_ms` 从索引循环开始计时；`/usr/bin/time -l` 为整个进程用时/RSS，两者分别报告。所有 MiB 均按 1,048,576 字节。

## 3. 全量分析和重用

| 指标 | 原始交互预算扫描 | 优化流式分析并写 pack | 当前生产 SQLite 全量命令 |
|---|---:|---:|---:|
| 完成文件 | 6,722 / 6,723 | 6,723 / 6,723 | 6,723 / 6,723 |
| 内部 wall | 9.626 s | 10.914 s | 14.740 s |
| 进程 real | 10.78 s | 11.99 s | **15.47 s** |
| 峰值 RSS | 35.91 MiB | 32.45 MiB | **35.94 MiB** |
| 峰值计费语法驻留 | 20.97 MiB，最多 8 文档 | 12.46 MiB，1 文档 | 同样单文档流式策略，未单独采样该字段 |
| 持久化 | 无 | 初始 pack 17.80 MiB | **66.63 MiB**，含二级索引 |

原始扫描的 `disas/nanomips.c` 为 713,872 字节，超过交互 512 KiB 预算，因此失败；本轮 bulk 明确使用 2 MiB/文件、单文档、10 秒协作工作预算，未静默跳过该文件。交互冷解析仍保留原 512 KiB 预算；已有大文件快照可在 2 MiB 文本预算内直接恢复。

流式结果包含 **81,174 个定义、371,627 个显式调用点**。解析累计 6.304 s、提取 2.025 s、编码与本地依赖采集 0.869 s。优化将遍历期间时钟检查改为每 256 节点加结尾，减少逐节点系统时钟开销；批处理不保留之前文件 AST，事实用 Arc 共享。原版提取累计 2.499 s，但覆盖不同，不能据此宣称严格的 19% 整体加速。

**不能将 9.626 s 和 14.740 s 直接比较后说优化变快或变慢**：后者覆盖更多文件，且新增编码、磁盘、定义/名称索引和事务。完整持久化成本已显式计入。

未变化再次运行全量命令：6,723 文件全部复用，**解析数 0，内部 1.287 s，进程 real 1.29 s，峰值 RSS 12.28 MiB**。仍需读取约 65 MB 源码、计算内容指纹并校验事实块；不是仅以 mtime 判断，也不等同于普通启动必须做全库检查。

正常 UI 打开不会先跑这个全量命令，只按需读当前文件。一次成功遍历后，CLI 清理已不存在文件；遍历出现错误时不以残缺清单删除记录。

### 精度限制

**3,044 个文件包含 grammar 的 syntax error 标记。** 宏、条件编译、代码片段、语言扩展及缺少编译环境均可能导致该状态。“全部生成快照”不代表“全部代码已精确理解”。调用目标仍为 unresolved；函数指针、虚调用、宏展开、C++ 模板和跨语言桥接未完成语义绑定。接近 Understand 的精确分析必须在后续接入编译信息与 A2 提供器，并单独建立性能基线。

## 4. SQLite 与替代后端的同数据比较

### 构建与磁盘

| 后端 | 具备能力 | 首次存储阶段 | 初始稳态大小 |
|---|---|---:|---:|
| SQLite raw | 路径/hash/校验/payload | 0.113 s | 22.64 MiB |
| SQLite indexed | raw + 定义/名称候选/依赖/热度表 | 约 3.88 s，不含热度导出 | **64.13 MiB** |
| append pack | 路径目录 + 连续 payload；无完整二级索引 | 分析阶段追加与发布累计 0.118 s，不含统一编码成本 | 17.80 MiB |
| hybrid indexed | SQLite 同等二级表 + 外部分段 payload | **6.260 s** | 59.04 MiB |

SQLite indexed 导入阶段总 wall 4.340 s，其中还包含 top-1000 热度导出约 0.461 s；put_batch 累计 3.857 s。不能拿 raw 的 0.113 s 代表完整关系索引成本。

上表统一导入按排序路径、每 32 文件提交。生产 CLI 的 WalkDir 顺序与按字节批次不同，数据库页布局不同，因此其 66.63 MiB 与同数据导入的 64.13 MiB 略有差异。数字均为 checkpoint 后文件长度，不是块设备实际写入量；WAL 在导入阶段使完整 SQLite 暂时达到约 75.84 MiB，长期写入还需监测 checkpoint 和碎片。

事实 payload 总计 17,234,012 字节，约 16.44 MiB。完整库剩余空间主要是可查询二级数据与 SQLite 页/索引成本，不能靠移动 payload 到文件段全部消除。pack 还需要约 **2.65 MiB 的目录内存估算**，并非零内存；早期分析阶段的旧估算未含依赖字符串，后续 export 数据已修正，报告采用修正版。

### 随机读取

下表为每一轮的 **p95 微秒**，包含 payload 校验与解码。第一轮也可能受之前写入和文件页状态影响，不能标成冷盘。

| 后端 | 快照 round 0 / 1 / 2 | 读取源码 + hash + 快照 round 0 / 1 / 2 |
|---|---:|---:|
| SQLite indexed | 1,166 / 67 / 59 | 331 / 93 / 110 |
| hybrid indexed | 200 / 52 / 50 | 82 / 81 / 83 |
| append pack | 44 / 44 / 45 | 81 / 75 / 75 |
| SQLite raw | 824 / 59 / 59 | 90 / 103 / 88 |

SQLite indexed 在重复读的快照 p95 为 0.059–0.067 ms；第一轮约 1.166 ms，仍满足当前交互需求。混合方案降低部分首次触达延迟，但稳态差距很小。纯 pack 打开需载入整个目录，约 3.4–4.2 ms；SQLite 连接打开约 0.4–2.2 ms，不需载入全库事实。

生产 Worker 链路另测 1,000 文件：读取源码、hash、线程队列、SQLite/热事实读取和 Engine.restore，**p50 0.258 ms、p95 1.354 ms、p99 3.370 ms；解析数 0，失败 0**。不含 JSON stdio、Swift 解码、文件树、排版和屏幕呈现，不能当作 UI 打开时间。末次事实池 9.01 MiB，元数据估算 0.48 MiB；手动总预算 16 MiB，事实池上限 9.6 MiB。该进程峰值 RSS 27.02 MiB。

真实 serve stdio 另做一次诊断：`system/vl.c`、`disas/nanomips.c`、`hw/acpi/aml-build.c` 均为 SQLite 恢复，parse=0；含 Python JSON 编解码与完整文本/事实传输约 4.98 / 20.19 / 5.01 ms。大文件传输不能用小 payload 读速代替。工作空间扫描 10,341 文件，未截断；critical 控制验证生效预算降至配置 16 MiB 的 1/8。它是单次协议诊断，不是 UI p95。

### 更新与可靠性

相同 100 个快照，每 10 个一批替换；SQLite 使用 FULL，pack/hybrid 在发布元数据前 sync 数据：

| 后端 | 100 次替换 wall | 文件增长 |
|---|---:|---:|
| SQLite raw | 1.939 ms | 0 |
| SQLite indexed | 284.913 ms | 8,192 B |
| hybrid indexed | 155.262 ms | 212,444 B |
| append pack | 167.393 ms | 196,060 B |

这是**相同快照替换**，不包含实际改函数、解析、失效传播；仅反映一次写入路径，未提供多轮置信度。文件增长不是设备写入放大。混合更新有收益，但每次追加旧 payload，若没有 GC 会持续膨胀。SQLite 在事务中统一替换文件快照和二级行，成熟的 WAL/恢复工具减少了首版维护面。[SQLite WAL 官方文档](https://www.sqlite.org/wal.html)

SQLite 默认 NORMAL 用于可重建缓存；断电可能丢失近期已提交事务，应用崩溃一致性与断电耐久性不能混称。需要更强耐久的用户资产另存。单写者仍是限制，后续后台分析要聚合短批次，不可把每条调用各开一个事务。

真实库已检查 integrity_check，路径快照使用主键，定义按文件使用 def_path，名称候选反查使用 calls_name 覆盖索引，查询计划随原始 JSON 保存。

## 5. 自定义格式做了什么，还缺什么

### 共有事实块

`SWF1` 4 字节 magic + bincode 2.0.1 standard 编码（小端、变长整数）。存储元数据包含源码 BLAKE3、payload BLAKE3、源码长度和分析器键；decode 上限 64 MiB，检查 magic、校验和、长度与尾随字节。它是应用的版本化事实格式，不是 Rust 对象原样内存转储，不存 Tree-sitter 内部指针/AST。

### append pack 实验

`snapshots.pack` 以 `SWPACK01` 开头，后续为连续 payload；`snapshots.dir` 保存版本、分析器键及按路径组织的 hash、校验、长度、偏移和依赖。目录解码上限 32 MiB，payload 读取检查文件边界。先 sync pack，再写临时目录、sync、原子 rename，Unix 同步父目录。更新追加新块，目录指向最新版本。

它易于顺序写/按偏移读，避免大量碎文件，但目录整体驻留、每次发布重写目录，也没有完整全局关系索引。当前没有多进程写锁、GC、分代分页目录、压缩或 Windows 原子替换验证，不能直接用于宣称超大规模生产可靠性。

### hybrid 实验

`facts.segment` 以 `SWHYBR01` 开头；payload 追加并 sync 后，同一 SQLite 事务更新 hash、偏移/长度与二级行。事务失败留下不可达尾部，旧指针保持有效。已有失败事务回归测试；没有做进程随机强杀/断电注入、跨平台故障矩阵和 compaction，仍是原型。

### 继续评估的替代路线

LMDB/MDBX 适合有序 KV 和直接映射读取，但仍需自行维护复合查询、次级关系和事务发布规则；RocksDB 类 LSM 适合高吞吐写入，但后台压缩、内存和写放大需单独控制；定制 CSR/倒排段可帮助巨大静态图遍历，但在线增量、删除遮蔽、代际一致性和合并复杂。这里是候选评估，没有实测这些后端，也不将其写成性能结论。

先优化 SQLite 中的 ID、索引冗余、批次与热度物化，再决定是否搬迁事实块。未来真正的图关系层可以单独使用邻接段，保留 SQLite 管事务元数据和用户状态，避免为一个瓶颈重写所有存储。

建议后续迁移触发条件（工程门槛，非本轮已达结果）：10 倍/100 倍真实样本下，有索引的文件恢复 p95 持续超过 10 ms，且 profile 证明确实由存储主导；或者写队列/锁竞争持续积压、checkpoint 明显影响前台；或者图遍历工作量已超出局部 SQL 访问模式。届时要求完整混合方案在相同功能/耐久配置下给出稳定收益，并通过恢复与回收测试再切换。

## 6. 热缓存、预读的收益与代价

### 缓存策略回放

合成轨迹：8 个 block 热文件反复阅读 + 扫描扰动，共 9,840 次请求。总配置 2 MiB，事实池 1.2 MiB；三轮交替策略次序。不是用户真实使用日志。

| 策略 | 命中 | 命中率 | 第 1 / 2 / 3 轮 wall | 末次计费事实 / 元数据 |
|---|---:|---:|---:|---:|
| LRU | 3,704 | 37.64% | 342 / 133 / 132 ms | 1.17 / 0.18 MiB |
| 采样频率 + 字节 | 3,840 | 39.02% | 142 / 142 / 141 ms | 1.20 / 0.24 MiB |

首轮 LRU 受页面首次触达影响，不能宣称频率策略快 2.4 倍。重复轮次中频率策略多约 6%–8% CPU/总耗时，命中率提高 1.38 个百分点，保留更多小事实项。当前保留此策略以满足热项保护，但收益尚不强，后续需要真实导航日志与消融对比；不能把命中率增加直接宣传为用户等待减少。

### 预读回放

人为构造“打开 C 文件后继续打开它的本地 include”轨迹，1,492 次请求，总配置 8 MiB：

- 关闭：795 命中（53.28%），总 wall 17–21 ms，前台 p95 43–51 μs。
- 开启：1,092 命中（73.19%），408 次预读准入、297 次实际使用（按项 72.79%），额外 payload 216,993 B；总 wall 42–47 ms，前台 p95 39–42 μs。
- 已淘汰未使用预读的计费内存 166,799 B，与磁盘 payload 字节属于不同口径，不能相除当浪费率。仍驻留未使用项不计已淘汰浪费。

这是对 include 预测友好的上界样例：前台收益较小，总工作量增加明显。实际随机 Worker 测试中 745 个预读项只有 114 个被使用，其他项大多仍留缓存，不能将其全部立刻判作浪费。首版限制空闲执行、每次候选/字节和 10% 推测事实池，并提供开关；后续应加入基于有效使用收益的自动降级和导航证据，不能扩大为无条件全库预读。

### 动态预算与内存口径

默认 auto 上限 64 MiB，初始生效 32 MiB；注入 warning 后 16 MiB、critical 后 8 MiB，预读暂停。恢复 normal 不立即膨胀，至少 30 秒且新增需求未命中后逐步增加。注入测试无后续未命中，因此 normal 后仍保持 8 MiB，符合滞后策略。manual 正常时使用手动值，压力时仍缩减；off 关闭附加事实池。

已解码事实按估算容量计费，metadata 单报；SQLite 页缓存、活动源码/AST、Arc 外部引用、写队列与 UI 另计。自动控制目前管理附加事实池与 SQLite 页预算，活动引擎仍有独立预算；没有把它包装为整个进程 RSS 的硬上限。macOS 的压力来源是 [DispatchSourceMemoryPressure](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure)，不是简单按物理内存百分比猜测。

当前 `used_bytes` 包含事实容量、条目和路径估算，metadata 粗估与条目部分重叠；它们用于预算/诊断，不是可直接相加的独占堆分配统计。Worker 测试程序还保留了用作样本清单的 pack 目录，其 RSS 包含这部分测试开销。后续需加入分配器级采样和共享所有权归因。

## 7. 双维热度与可用输出

每个文件/符号输出独立列：`syntactic_incoming_proxy`、`ambiguous`、`resolved_incoming`、`evidence_level`，以及 `active_ms`、`open_count`、`attention_score`、`last_seen`。结构列不会随用户阅读衰减，用户关注按 7 天半衰期衰减。API 支持按结构候选或阅读关注分别排序。

本次导出 **81,174 个符号、6,723 个文件**，位置为：

- `build/benchmarks/qemu-v1/symbol-heat.csv` / `symbol-heat-all.json`
- `build/benchmarks/qemu-v1/file-heat.csv` / `file-heat-all.json`

真实用户事件尚不存在，所有关注时长/次数为 0；synthetic replay 和诊断没有写入 usage。读者可以按关注列排序，但不会看到伪造的“用户热门函数”。这些大文件作为生成产物保留在 build，不塞进设计文档。

结构代理仅对简单标识符的调用拼写计数；同名项收到同一候选计数，并标歧义，不能直接相加求出精确项目入度。例如 Coverity 模型文件中的库函数定义会得到很高的名字候选热度，不能据此判断该模型文件是运行架构中心。`resolved_incoming=null`，真实 A2 指标保持 unknown。文件结构值为其去重函数名称的候选提及总和，跨文件仍可能重叠。

符号关注身份由相对路径、各级作用域种类/名称/同名序号编码后 hash 生成，避免行号移动或重复条件作用域直接碰撞；它不是编译器 USR。重命名、移动、重排同名作用域可能改变身份，需要未来 A2/重构映射，旧行为行目前不做自动合并。

macOS 设置可关闭采集和清空当前项目记录。约 5 秒采样且限制前台/可见/焦点/空闲条件，最多有一个心跳的归因误差；不记录键盘内容。完整双热度浏览表/图谱配色仍属于 UI 设计下一步，本轮提供数据/API/导出和设置，未伪装已完成图谱界面。

## 8. 正确性验证、复现与剩余工作
