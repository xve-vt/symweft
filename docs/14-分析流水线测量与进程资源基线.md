# 分析流水线测量与进程资源基线

日期：2026-10-19。对应 [任务清单](13-任务分解与验收清单.md) 的 PERF-01。本轮建立可复现的测量入口，校准阶段和进程口径；没有将测量工具称为分析算法优化。

## 1. 已实现的测量入口

- `SYMWEFT_PROFILE=1`：Core 和一次性编译 worker 开启诊断计时，默认关闭。需要在启动 Core 前设置，进程内不动态切换。
- 索引 job 增加可选 `profile`：最近最多 64 个 TU 的阶段、记录数量、截断标志和 checkpoint 时间。不是全库无界追踪。
- 异步 preview 增加可选 `profile`：编译/传输/解码和结果发布前验证。既有 `wall_ms` 保持可用于开关探针对照。
- `scripts/resource_probe.py`：通过 macOS libproc 采样指定根进程及其后代，区分 UI、Core、compiler_worker 和 helper。不运行每帧 ps，也不记录机器上其他应用的命令行。
- `scripts/benchmark-analysis-pipeline.py`：QEMU 两个真实 TU 的首次索引、复查、未保存预览、查询、Core 空闲、探针开关对照，以及原生窗口分析/空闲。
- 原生开发参数 `--perf-idle-to <路径>` / `--perf-refresh-indexed true`：使用已有工作台和 Core 协议，刷新已索引范围后进行空闲测量。诊断参数使用显式值；不是新产品按钮，不扩大到整个编译数据库。

相关实现：[计时类型](../crates/symweft-semantic/src/profile.rs)、[工作进程](../crates/symweft-semantic/src/service.rs)、[事实存储](../crates/symweft-semantic/src/store.rs)、[资源探针](../scripts/resource_probe.py)、[生产测量检查](../scripts/check-performance.py)。

语义提供器身份、SQLite/SMF2 事实格式和现有协议版本保持不变。诊断数据只存在于运行结果，不被加入符号身份或持久化事实载荷。

## 2. 阶段计时口径

### 编译 worker

| 字段 | 范围 |
|---|---|
| prepare_micros | 提供器身份、参数、SDK 和未保存输入准备 |
| parse_micros | 创建 Clang index 及解析 TU |
| diagnostics_micros | 读取编译器诊断 |
| fact_extract_micros | 遍历 AST 并提取事实 |
| input_validation_micros | 收集实际加载输入、内容对照及摘要 |
| provider_wall_micros | 提供器函数内部总时间，测量点在 TU 析构之前 |
| request_decode_micros | 解码父进程请求 |
| reply_encode_micros | 流式序列化总时间减去转发 writer 调用时间；包含探针管理开销 |
| stdout_write_micros | writer 调用、缓冲复制、flush 与管道反压；不是纯内核传输时间 |
| worker_wall_micros | worker 读取请求至结果写出后的墙钟；包括提供器返回时的析构，末尾资源报告自身不计入 |
| cpu_user_micros / cpu_system_micros | 该 worker 自身的 getrusage 累积 CPU，不含子进程 CPU |
| self_peak_rss_bytes | 该 worker 自身截至结果写出后的 RSS 高水位 |

保留旧 `Snapshot.extract_micros` 的兼容语义，它仍包括输入验证等后处理，不能与新的 fact_extract_micros 当成同一指标直接比较。

### Core 和持久化

Core 分别报告请求编码、spawn、stdin 写入、child_wait、回复解码、结果有效性复核和总墙钟。child_wait 与 worker 执行和输出读取重叠，不能与 worker 各阶段相加得到总时间。

存储报告 publish_wall、事实 bincode 编码、BLAKE3、压缩、复用事实验证、commit 和 sqlite_and_other。小事实操作先累加纳秒，避免每条取整为微秒后大量变成 0。sqlite_and_other 是扣除已测子阶段后的残差，包含身份字典、SQL、元数据及探针开销，**不是 SQLite 的纯磁盘 I/O 时间**。commit 也不等于一次物理落盘或断电持久性保证。

checkpoint 单独计时。查询使用生产 stdio 的端到端延迟，包含配置/输入验证、查询/解码、序列化、IPC 和客户端处理；不与内部 store.query_micros 混为同一范围。

编码耗时无法准确地放回“已经完成编码的同一份字节”。worker 因此保留原有流式 JSON 写法，通过有界 stderr 诊断行回传计时；父进程只接受匹配当前子进程 PID 的记录，不为了测量额外构造完整回复缓冲区。

## 3. 修正的资源口径

此前父进程读取 RUSAGE_CHILDREN，得到的峰值可能包括更早回收的子进程。本轮移除这项混合：开启 profile 时用当前 worker 自报的峰值；未开启时旧快照字段仅是提供器提取结束前取得的自身高水位，不代表整个进程树峰值。

外部采样使用安装 SDK 中的 rusage_info_v2，记录当前 RSS、physical footprint、自身 CPU、磁盘归因计数和原生启动标识。PID 与启动标识共同识别进程，避免 PID 重用后采到不相关应用。父子 CPU 分别读取自身字段，不把 child_cpu 再叠加一遍。

角色按当次父子关系和可执行文件名判定；fork 后 exec 前可能暂记为 helper，同一进程身份因此可能出现在多个角色的历史诊断中。每轮进程树只计一次该身份，不能按角色历史峰值再次汇总。

Apple Silicon 上 CPU 计数需要按 Mach timebase 换算，不能直接当纳秒。检查程序通过实际 CPU 工作与 getrusage 交叉校准，且测试了 ABI 大小和真实父子进程发现。参考：[Apple Mach 时间单位说明](https://developer.apple.com/library/archive/qa/qa1398/_index.html)、[Apple libproc 实现](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.c)、[XNU 资源实现](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_resource.c)。

默认请求每 50 ms 采样，实际平均/最大间隔另记。每轮读取多个进程存在短暂时间差，collection_micros 表示采集窗口；采样高水位不是真实瞬时峰值。上限为 128 个进程、每次最多 512 个直接后代，内存最多保留 20000 帧；原始 JSONL 流式写盘，截断和历史覆盖明确报告。

- tree_rss_sampled_max 是**同一轮进程 RSS 之和的最大值**，共享页可能重复计入，不等于独占物理内存。
- tree_footprint_sampled_max 是同轮原生 footprint 计数之和，也不作为唯一物理页集合的证明。
- 各进程/角色的独立最大值只用于诊断，不能相加冒充同时总量；也不能将 headless 分析和另一时刻 GUI 空闲相加。
- CPU 百分比以一个逻辑 CPU 为 100%，不按整机核数归一。新出现、退出和相位边界的不可完整区间有标志；观察到的 CPU 增量可能低于整个生命周期 CPU，短 worker 可由其自报补充，但两者不能重复求和。
- 无进程样本时标 available=false、相关总量为 null；不能把短于采样间隔的任务解释为零占用。
- GPU、WindowServer 及其他系统服务没有被归因到应用。GPU 状态为未测，不是 0；GPU 图谱专项仍属于 GRA 任务。

探针是独立基准进程的一条线程；线程 CPU、采集时长和整个基准程序的 peak RSS 单独记录，不计入产品进程树。该 peak RSS 包括 Python 客户端、原始轨迹和报告生成，不能全归因于采样器。

## 4. 探针对运行的影响

默认运行不启动资源采样器，也不做每事实/每次写入计时。显式开启后，流式 writer 的许多小调用都要计时，观察者开销不可忽略；存储事实的细粒度计时也有开销。

基准因此交错运行默认三组 profile off/on 预览，记录同一磁盘输入的后台墙钟与就绪时间。该对照只覆盖本机该 TU 的预览，OS 缓存不清空，不能解释为普遍常数或稳定 p95。后续优化应同时比较**关闭探针的实际速度**和开启探针后的阶段分布，不以诊断模式耗时宣称正常路径退化或加速。

原生模式保留正常 750 ms 语义维护和 5 秒资源/压力定时器，合成运行不记录真实阅读关注、不写外观/缓存偏好。沿用应用正常的启动激活行为，报告窗口可见、遮挡和活动状态，不能把前台和被遮挡的窗口当作相同图形负载。

## 5. 本机范围与实测

## 6. 复现与验收

```sh
SYMWEFT_BUILD_CONFIG=release bash scripts/build-macos.sh
python3 scripts/check-performance.py
python3 scripts/benchmark-analysis-pipeline.py
```

需要此前已经生成的 QEMU 编译数据库和生成依赖；不会重新执行项目构建或自动分析 2855 TU。默认报告在 build/performance 的新目录，不覆盖已有缓存；`--output` 可指定新目录，`--interval-ms` 可设 25..1000，`--idle-seconds` 可设 6..30。`--skip-ui` 仅用于局部检查，不能作为包含原生进程的完整 PERF-01 验收。

完整产物包括 pipeline.json、Core/native JSONL、原生阶段报告及标准输出/错误。跟踪 stderr 中的 PERF_PROBE 生命周期事件可区分窗口尚未进入启动回调、Core 故障、分析失败与空闲测量；失败或超时运行不会写成成功基线。

测量检查四项均通过：同轮峰值/相位边界聚合、原生 CPU 单位校准、实际父子进程及回收、生产 profile 开关语义等价和编译失败诊断。32 项 Rust 测试、clippy、生产语义/实时/预览协议、Swift foundation、原生浅/深主题外部保存回归均通过。release 应用重新构建，最终完整测量通过，磁盘源码逐字节未变。验证记录同时归档在原始 JSON。
