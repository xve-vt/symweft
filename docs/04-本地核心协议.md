# Symweft 本地核心协议 v1

当前实现：Rust core 独立进程，Swift 前端通过 stdin/stdout 的 UTF-8 JSON Lines 通信。每个 core 进程维护一个活动工作空间。

## 请求与响应

每行一个 JSON 对象，末尾换行；id 为无符号整数。stdout 仅输出协议，诊断写 stderr。

~~~json
{"id":1,"method":"initialize","params":{}}
{"id":2,"method":"workspace.open","params":{"root":"/absolute/project"}}
{"id":3,"method":"document.read","params":{"path":"src/main.rs"}}
{"id":4,"method":"document.open","params":{"path":"src/main.rs"}}
{"id":5,"method":"analysis.at","params":{"path":"src/main.rs","revision":1,"byte_offset":10}}
~~~

成功响应含 id、protocol_version、result；失败响应含 id、protocol_version、error（code/message）。无法解析 id 时返回 null。

## 当前能力与约束

- initialize：版本、能力、限制；analysis_level=syntax_on_demand。尚无 A2 语义绑定。
- workspace.open：规范化目录、扫描相对路径、语言标签、大小与数量；成功后替换活动工作空间。
- workspace.open 的 analysis_level=text_only 表示本次扫描只枚举文件，不表示已经分析整个工作空间；单文件通过 document.open 获得 syntax 快照。
- document.read：仅读取活动工作空间中的普通 UTF-8 文本。拒绝绝对路径、父目录跳转、越界 symlink、NUL 二进制与超过 2 MiB 的文件。
- document.open：读取一次磁盘文档，并按需进入共享语法引擎。返回 document、analysis、update、analysis_error；不支持语言/超过分析预算时后三项相应为空，文本仍可阅读。
- document.edit：以内存事务更新已分析文档，参数为 path、base_revision、start_byte、old_end_byte、new_text；返回 analysis、update。不写入磁盘，不改扫描快照；再次 document.open 会以磁盘内容对齐当前缓存。macOS 当前 UI 仍只读。
- document.close：释放该路径热缓存，返回 closed；已淘汰路径返回 false。
- analysis.get：参数 path、revision，获取该修订的定义与调用点快照。
- analysis.at：参数 path、revision、byte_offset，返回最近包含该位置的 symbol、call 和 revision；无匹配为 null。嵌套调用优先内层。
- analysis.stats：进程内累计的解析/无变化命中/淘汰计数，以及当前缓存文档数、源码字节与估算保留量。
- 扫描不跟随 symlink，最多 20,000 个文件/目录条目，深度最多 32；达到限制时 truncated=true。不可读与跳过链接另计 skipped_entries。
- 默认跳过 .git、.build、.swiftpm、target、node_modules、build、dist、.venv、venv、__pycache__、.gradle、.idea、.DS_Store。尚未实现 .gitignore 规则解释。
- 请求最多 4 MiB；超大请求报错后关闭连接。客户端响应缓存最多约 16 MiB、响应超时 30 秒。
- 当前用于受信任的本机项目阅读，不是针对恶意并发修改文件系统的操作系统沙箱；路径竞争仍需平台原语加固。
- line_count 使用“换行符数 + 1”的编辑器定义，空文件有一行，末尾换行保留空末行。
- 当前无磁盘保存、索引订阅、文件监听或取消请求；刷新重新扫描，后续版本显式协商新能力。服务仍顺序处理请求，不得在同一循环中追加阻塞交互的全量语义分析。

## 语法事实与增量契约

支持 Python、C、C++、Rust、Java；.h 当前默认使用 C grammar。analysis 包含 path、revision、language、level=syntax、facts。facts 包含 symbols、calls、has_syntax_errors。

- symbols：常见定义的 local_id、name、kind、range、name_range、parent_id、is_callable。local_id 仅在该文档修订内有效，不是稳定语义 ID。
- calls：callee（受限长度的源码拼写）、kind、range、owner_id、evidence=syntax、resolution=unresolved。owner_id 是调用点在函数/闭包体中的语法归属，不表示绑定了目标或证明运行时一定调用。
- 所有 range 为零起点 UTF-8 字节的 [start_byte,end_byte)，start_line/end_line 是从 1 开始的展示行号。拒绝字符中间的偏移。AppKit 必须转换为 UTF-16 后使用。
- update：revision、mode（cold/incremental/unchanged/restored）、parse_micros、extract_micros、total_micros、changed_range_count。restored 表示从已验证的持久化/事实缓存恢复，无 AST，parse/extract 为 0；耗时仅含引擎，不含读盘、IPC 与 UI；changed_ranges 不等于所有文本变化范围。
- revision 为进程内单调递增 token；相同内容返回相同修订，关闭/淘汰重开或切换工作空间后不会复用旧修订。进程重启需重新打开文档。
- 未缓存路径返回 analysis_missing；版本不符返回 stale_revision；UTF-8 编辑/位置不合法返回 invalid_edit/invalid_position。预算失败不发布部分结果，之前成功的修订仍可查询。
- 默认最多 8 个热文档、4 MiB 热源码、512 KiB/分析文件、64 MiB 估算缓存、20,000 个事实/文件、200,000 遍历节点/文件、200 ms 协作式工作预算。估算缓存不是 RSS 硬上限，详见引擎设计。

编辑示例（偏移必须对应真实内容）：

~~~json
{"id":6,"method":"document.edit","params":{"path":"src/main.rs","base_revision":1,"start_byte":3,"old_end_byte":7,"new_text":"entry"}}
{"id":7,"method":"analysis.get","params":{"path":"src/main.rs","revision":2}}
{"id":8,"method":"document.close","params":{"path":"src/main.rs"}}
~~~

## 兼容策略

前端启动先握手，验证协议版本与响应 id。业务错误保留连接；传输错误关闭该 core 并提示重新打开工作空间。未声明能力不向用户展示为已完成。

JSON Lines 是第一阶段可观察的开发传输。未来大批量索引事实采用流式分页/二进制批次，通过版本协商演进。

## A1 持久化、缓存与热度扩展（已实现）

`document.open` 新增可选 `storage`：`source=analysis/sqlite/memory`、`load_micros`、`persistence=queued/reused/unavailable`。当前文本内容读取后计算 hash，匹配才复用；恢复后的 revision 是新进程修订，不能复用旧 token。queued 只表示写入入队，不等于已经持久化。第一次编辑 restored 文档会按需建立语法树，此后才是树增量。

| 方法 | 参数 | 响应/含义 |
|---|---|---|
| cache.configure | mode=auto/manual/off，max_bytes=1024..1073741824，prefetch=bool | 生效设置与统计；macOS UI 提供 8..1024 MiB |
| cache.status | 无 | settings、cache、sqlite_version、pending_prefetch、queued_payload_bytes、last_write_error |
| cache.pressure | level=normal/warning/critical，busy=bool，now_ms=单调时钟毫秒 | accepted；不修改用户设置，调整实际生效预算 |
| usage.record | path、revision、可选 local_id、active_ms、opened=bool | queued；必须对应当前已分析修订，时长截断为最多 5 秒 |
| usage.clear | 无 | cleared；清空当前工作空间阅读关注，保留结构索引 |
| heat.query | kind=file/symbol，sort=structure/attention，limit | evidence=syntax_proxy、rows；limit 限制在 1..100000 |
| index.flush | 无 | flushed；等待前序写入并 checkpoint，存在写入错误则返回 index_error |

cache 包含 `effective_bytes`、`fact_limit_bytes`、`used_bytes`、`metadata_estimated_bytes`、entries、hits、misses、evictions、bypasses、prefetch_admitted/useful/wasted_bytes、pressure。事实字节为估算，且不含活动引擎额外引用、AST、UI 和 RSS。自动内存压力目前只管理事实池与 SQLite 页预算。

heat rows 包含 entity_key、path、name、kind、syntactic_incoming_proxy、ambiguous、resolved_incoming=null、evidence_level，以及 active_ms、open_count、attention_score、last_seen。结构候选与阅读关注分别排序；静态名字候选不是运行时频率，也不是已解析入边。last_seen 为 Unix 秒；attention_score 在读取时按 7 天半衰期衰减。

~~~json
{"id":20,"method":"cache.configure","params":{"mode":"manual","max_bytes":16777216,"prefetch":true}}
{"id":21,"method":"cache.pressure","params":{"level":"warning","busy":false,"now_ms":123000}}
{"id":22,"method":"heat.query","params":{"kind":"file","sort":"structure","limit":100}}
{"id":23,"method":"index.flush","params":{}}
~~~

`symweft-core index <root>` 为独立批处理命令，输出 JSON 汇总，不在 serve 的交互循环执行。使用相同平台索引路径；full scan 按 hash 复用，批次替换，完整遍历后删除已不存在文件。读取/分析失败逐项报告，调用者应检查 failures；当前不是带文件监听的持续后台索引器。

## C/C++ A2 编译器语义（首版已实现）

与 A1 独立，证据为 `clang_semantic`；完整实现、预算、存储和 QEMU 范围见 [语义报告](10-C-Cpp语义闭环与QEMU验证.md)。必须先 workspace.open，再导入真实构建配置；不执行数据库中的 shell/编译命令。

| 方法 | 参数 | 行为 |
|---|---|---|
| semantic.configure | compile_commands，timeout_seconds?，worker_memory_mib? | 导入配置，返回 configured_units、rejected、provider、limits、job、index；不会自动全量解析 |
| semantic.index | paths? 数组，limit? | 异步启动；空 paths 表示全部已配置 TU，源码选择该 TU，已索引头文件选择其已知包含者；返回 started/total |
| semantic.progress | 无 | 轻量 configured/configured_units/rejected_units/job，适合 UI 轮询 |
| semantic.status | 无 | 详细配置、上次记录的单元状态与统计；configuration_matches 不代表全库所有输入均未变化 |
| semantic.cancel | 无 | 设置取消请求，工作进程回收后任务进入 cancelled；应继续读 progress |
| semantic.symbols | name，limit? | 精确名称检索；名称用于寻找候选，关系连接使用 id |
| semantic.at | path，byte_offset | entity_id、declarations、references、enclosing_functions；保留各 TU 变体 |
| semantic.relations | entity_id，direction，limit? | direction 为 definitions/declarations/references/incoming/outgoing |
| semantic.invalidate | path | 标记已索引相关单元过期；不会自动开始分析 |
| semantic.preview | path，revision，unit_id? | 对当前引擎缓冲区做语义预览；overlay=true、persisted=false，含 snapshot/diagnostics；多变体需要指定 unit_id |

job.state 为 idle/running/complete/complete_with_errors/cancelled，包含 total、analyzed、reused、failures；运行中另有 completed。complete 只表示所选工作成功，不能据此推断全项目覆盖。

configure/status 另有 `incompatible_provider_units`，统计最后记录为 current、但编译器/SDK/include 环境指纹不匹配的单元数量。UI 提示重新分析，这些贡献不会被当作当前关系返回；该数量不包括其他输入内容过期情况。

符号含 id、usr、name、kind、signature、definition、callable、location、extent；引用含 target；调用含 caller、target、resolution、location、spelling。位置用绝对路径和 UTF-8 字节 `[offset,end_offset)`，line/column 从 1 开始。持久化查询行增加 unit_id、main_file、input_key、freshness；调用尽可能提供 caller_name。

`semantic.at.entity_id` 仅在返回候选具有唯一实体身份时赋值；不同 TU/变体指向不同实体时返回 null，客户端需从 references/declarations 中按 unit_id 选择，不能默认采用第一个结果。

resolution 为 direct/virtual_candidate/indirect/unresolved。direct 只说明绑定具体可调用声明，定义可能尚未索引；virtual_candidate 不是确定动态目标；indirect/unresolved 没有按名称猜测的目标。头文件关系可在多个 TU 重复出现，客户端必须保留变体上下文。

查询只返回已索引且其已加载输入通过指纹检查的贡献。`completeness` 提醒调用者仍可能存在未索引单元/变更；`freshness=included_inputs_validated` 不等于完整文件监听一致性。读取时使用固定数据库事务；实际源码文件不是操作系统原子快照。

limit 默认 100，限制为 1..1000；semantic.at 每类候选最多 32。索引单次最多选择 128 个路径。TU 默认 30 秒、512 MiB 采样 RSS 软上限，可分别设为 1..120 秒、32..4096 MiB。Windows RSS 限制尚未实现。语义查询不使用 A1 热池配额。

`document.edit` 使相关磁盘语义失效；预览只接受当前 revision。阅读器内容与磁盘不同，位置查询返回 stale_document。配置或响应文件变化需重新 configure。编译错误/超时/取消不发布半份当前快照，错误保留在 failures 中。旧 `semantic.preview` 保留同步兼容行为，工作进程忙时拒绝；新客户端应使用下述异步预览方法。

~~~json
{"id":30,"method":"semantic.configure","params":{"compile_commands":"/project/build/compile_commands.json","timeout_seconds":30,"worker_memory_mib":512}}
{"id":31,"method":"semantic.index","params":{"paths":["src/main.cpp"]}}
{"id":32,"method":"semantic.progress","params":{}}
{"id":33,"method":"semantic.at","params":{"path":"src/main.cpp","byte_offset":120}}
{"id":34,"method":"semantic.relations","params":{"entity_id":"<实际返回的实体 ID>","direction":"definitions","limit":100}}
~~~

CLI：`symweft-core semantic-index <root> <compile_commands.json> [paths...] [--limit N]`，等待任务并输出详细 JSON；有失败或取消时退出 1。`semantic-worker` 是内部子进程入口，不是构建系统执行器。

## 实时语义维护扩展

详见 [实时更新与查询优化](11-实时语义更新与查询优化.md)。提取器和事实载荷兼容上一阶段，增加：

| 方法 | 参数 | 响应/行为 |
|---|---|---|
| semantic.watch | enabled=false、auto_refresh=true、metadata_cache=true | 配置原生监听；布尔默认值如左；CLI 默认尚未启用，macOS 导入配置后启用 |
| semantic.refresh | 无 | 强制重新分析已记录单元，清理自动范围超限状态；不扩展到整个编译数据库 |

progress/status 新增 watch：`enabled/auto_refresh/metadata_cache`、monitor、pending_units、paused、pressure_paused、revision、invalidated_units、auto_jobs、manual_refresh_required、configuration_required、error、fingerprints、configuration_fingerprints、max_auto_units。monitor 包括 backend/roots/epoch/queued_paths/events/overflows/degraded。指纹统计包括 hits/hashes/bytes_read/evictions/entries/charged_bytes/enabled。

job 新增 trigger=manual/watch。所有语义请求消费待处理事件；index/refresh 不在用户请求前抢先调度自动任务，cancel 优先暂停。macOS 每 750 ms 请求 progress；不再发送请求的纯 serve 客户端只收集事件，不会自行解析。关闭/切换工作空间会释放监听和工作进程。

每次批次静默 350 ms、持续变更最多等待约 2 秒；自动范围最多 256 个已记录 TU，超过后标记过期并要求显式 refresh。事件路径最多 1024 项；溢出/need_rescan 保守失效已知范围。新头文件可能遮蔽旧 include，因此结构变化可能重建多个原本内容未变的 TU。

strict 每次读取输入内容；metadata_cache 仅在原生监听健康时启用，每次比较属性并按时限重新 hash，Unix 最多 2 秒、其他平台最多 100 ms。两个指纹池各最多估计 1 MiB 和 8192 项；这不是整个进程 RSS 上限。监听错误降级严格查询、暂停自动重建。

cancel 暂停自动任务并保留预算内待更新范围；再次 watch 可恢复。critical 压力取消活动工作并保留任务，压力恢复后继续，但不会撤销用户的取消。未保存 dirty 文档对应 TU 暂停自动发布；关闭丢弃缓冲区或保存后重新 open 才释放阻塞。编译配置变化需要重新 configure，refresh 不能绕过配置校验。

~~~json
{"id":50,"method":"semantic.watch","params":{"enabled":true,"auto_refresh":true,"metadata_cache":true}}
{"id":51,"method":"semantic.progress","params":{}}
{"id":52,"method":"semantic.cancel","params":{}}
{"id":53,"method":"semantic.watch","params":{"enabled":true,"auto_refresh":false,"metadata_cache":false}}
{"id":54,"method":"semantic.refresh","params":{}}
~~~

## 异步未保存语义预览

设计、资源口径与 QEMU 实测见 [异步预览与修订一致性](12-异步语义预览与修订一致性.md)。原有持久化格式、provider 身份及协议版本不变，capabilities 增加下列方法。

| 方法 | 参数 | 响应/行为 |
|---|---|---|
| semantic.preview.start | path、revision、documents?、unit_id?、memory_mib=32 | 返回状态和 ticket；异步编译，保留结果预算为 1..128 MiB |
| semantic.preview.progress | path、revision、job_id | 推进任务、检查当前修订/依赖，返回紧凑状态 |
| semantic.preview.at | path、revision、job_id、byte_offset | 当前 overlay TU 的上下文，拒绝错误 UTF-8 边界 |
| semantic.preview.relations | path、revision、job_id、entity_id、direction、limit? | 当前 overlay TU 的声明/定义/引用/出入调用，limit 同持久化查询 |
| semantic.preview.cancel | job_id | 取消该 ticket 并释放结果；迟到的旧 ticket 返回错误 |

ticket 包括 job_id/path/revision/unit_id。请求中的 path 应使用 document.open 的缓冲区键；ticket.path 为规范绝对路径。job_id 在 Core 进程内递增，重新配置不重用。

state 为 idle/queued/running/ready/failed/stale/cancelled。状态包括 ticket、reason、worker_active、queued、overlay=true、persisted=false、memory_budget_bytes、charged_bytes、wall_ms、parse_micros、extract_micros、clang_accounted_bytes 和 diagnostics。后四项在无结果时为 null；诊断最多 64 项，每条消息最多 1024 字符，reason 最多 2048 字符。progress/status 的顶层新增 preview 状态。

start 可抢占磁盘索引，保留预算内待维护范围；两个工作进程不会并行编译。最新请求替换等待项、取消旧运行项、释放旧结果。纯 serve 客户端需轮询推进。手动 index/refresh 和旧同步 preview 在异步预览活动时拒绝；通用 semantic.cancel 可取消所有语义工作。

预览只覆盖一个 TU。`documents` 是可选的 `[{path,revision}]` 数组，主 path/revision 必须包含在内；提供数组时，所有 dirty 缓冲区必须全部出现，Core 从 Engine 读取这些修订的当前文本并一起送入同一次编译，不会静默读取其他 dirty 文件的磁盘旧内容。未 dirty 的当前打开文档也可显式加入。缺少数组时保留单文档行为，另有 dirty 文档返回 `multiple_dirty_buffers`；旧同步 `semantic.preview` 不接受 documents，并在多 dirty 时同样拒绝。

documents 最多 16 项、单文档及合计源码均不得超过 8 MiB，initialize limits 公布上限。数量或字节超限返回 `overlay_budget`，漏掉 dirty 文档返回 `missing_overlay_documents`，重复路径或主文档不匹配返回 `invalid_params`，旧修订返回 `stale_revision`。结果证据为 clang_semantic_overlay，行附带 freshness=overlay、revision、preview_id、unit_id、main_file。旧 preview 查询不自动合并其他 TU 的磁盘定义和入调用，完整性标记明确此限制。

读查询先验证 Engine 当前修订，再检查 ticket 和依赖；旧修订返回 stale_revision，其他不匹配、未就绪等当前仍使用 index_error。文件打开/重载/关闭、继续编辑、结构/源文件事件、配置变动和 critical 压力都可能失效预览。critical 后需压力恢复再重新请求；取消后 worker_active 可能短暂为 true，直到旧工作线程被回收。

容量计费包含结果 Vec/String 容量，不是 RSS 硬上限；接收/反序列化峰值另计。超预算整份结果丢弃，failed 且 charged_bytes=0。新方法不返回完整 snapshot，避免大型 TU 把前端传输上限撑满。

~~~json
{"id":60,"method":"semantic.preview.start","params":{"path":"src/main.cpp","revision":7,"memory_mib":32}}
{"id":61,"method":"semantic.preview.progress","params":{"path":"src/main.cpp","revision":7,"job_id":1}}
~~~

## 统一语义查询版本（a2-query-v1）

`semantic.status/progress` 的顶层 `query_version` 表示当前持久化查询版本；`semantic.preview.start/progress` 及状态中的 `preview.query_version` 表示当前 overlay ticket 的查询版本。`semantic.symbols/at/relations` 和 `semantic.preview.at/relations` 的响应也携带与本次结果相同范围的 `query_version`。

`semantic.symbols/at/relations`、`semantic.preview.at/relations` 和 `semantic.preview.progress` 接受可选 `query_version` 参数。新客户端应把最近一次状态或结果中的完整对象原样带回，不要在客户端重组或只保留其中一个字段。未携带时仍按旧客户端兼容方式查询，但响应同样返回当前版本；后续项目级合并和分页接口可以要求必须携带。

~~~json
{
  "contract": "a2-query-v1",
  "workspace": "/absolute/project",
  "configuration": {
    "id": "<工作空间与编译数据库身份>",
    "content_key": "<解析后命令、响应文件摘要及拒绝项的内容键>",
    "provider": "a2-clang-v3:<libclang/SDK/环境身份>"
  },
  "disk": {
    "schema": "a2-store-v2",
    "store_id": "<持久化数据库随机身份>",
    "revision": 42
  },
  "documents": [
    {"path": "/absolute/project/src/main.cpp", "revision": 7, "content_key": "<缓冲区 BLAKE3>"}
  ],
  "coverage": {"kind": "overlay_translation_unit", "unit_id": "<TU 身份>"}
}
~~~

- `workspace` 是规范化工作空间根；配置 ID、配置内容键和 provider 分开比较，配置变化不能仅靠路径相同蒙混通过。
- `disk.revision` 随 TU 状态或事实贡献在同一 SQLite 写事务中推进。持久化行查询在与事实相同的读事务中取得基线，避免后台发布造成行与版本错配。
- `documents` 是参与查询的文档修订集合，按路径和修订排序；持久化范围为空数组，当前 overlay 可包含同一 TU 的多个主文件/头文件缓冲区。多 TU 文档集合和原子多结果切换仍属后续任务。
- `coverage.kind=persistent_index` 只覆盖持久化索引贡献；`overlay_translation_unit` 只覆盖指定 unit_id 的当前内存 TU；`overlay_with_persistent_index` 表示当前内存 TU 与其他有效磁盘贡献的项目级合并范围。原有 `completeness` 继续说明未索引单元、变体和未知目标等限制。
- `job_id/path/revision` ticket 校验仍然保留。查询版本标识事实输入与覆盖范围，不代替异步任务 ticket，也不以单个模糊 generation 代表全部身份。

契约标识不支持时返回 `unsupported_query_version`；工作空间、配置/provider、磁盘基线、文档集合或覆盖范围任一不一致时返回 `stale_query_version`，调用者应重新取得版本。缺字段、字段类型错误或未知字段返回 `invalid_params`。

磁盘基线是**语义 SQLite 的提交版本**，不是整个文件系统的原子快照。查询仍按既有规则复核贡献单元的已加载输入摘要并排除无效行；新增 include 搜索候选等情况仍依赖结构事件和重新分析。该边界与上述实时维护章节相同。

## 单 overlay 项目级合并查询

预览 start/progress/status 除原有 `query_version` 外，还返回 `project_query_version`。两者的工作空间、配置、磁盘基线和文档集合相同，后者把覆盖范围标为 `overlay_with_persistent_index`。项目查询必须携带完整的 `project_query_version` 作为 `query_version`，不能改用旧 preview 或 persistent 版本。

| 方法 | 参数 | 响应/行为 |
|---|---|---|
| semantic.project.at | path、revision、job_id、byte_offset、query_version | 当前 overlay 与其他有效磁盘贡献的合并上下文；每类最多 32 项 |
| semantic.project.relations | path、revision、job_id、entity_id、direction、query_version、limit? | 合并声明/定义/引用/出入调用；limit 为全局 1..1000 |

查询先检查当前 ticket、Engine 修订、依赖和 ready 状态，再按 ticket 的精确 `unit_id` 遮蔽该编译变体的旧磁盘贡献，合并当前 overlay 与其他通过 state/provider/输入摘要校验的磁盘 TU。preview 未就绪、失败或过期时返回错误，不回退到被遮蔽的旧边。当前 overlay 可包含同一 TU 的多个文档，但不代表多 TU 调度或未保存头文件包含者批量更新已完成。

响应顶层证据为 `clang_semantic_project`，包含 `overlay_unit_id`、`completeness` 和项目覆盖的 `query_version`。每一行另含 `evidence=clang_semantic` 或 `clang_semantic_overlay`，并保留 unit_id、main_file、freshness 及 overlay revision，合并不按实体或位置丢弃构建变体。`project.at` 根据合并后的引用/声明重新计算唯一 entity_id。

合并行当前以 overlay 在前、磁盘确定性顺序在后，再应用全局限额；这不是 OVL-10 的稳定分页，未索引单元、变化范围和候选目标仍受 completeness 约束。旧 `semantic.at/relations` 继续只查磁盘，旧 `semantic.preview.at/relations` 继续只查当前 overlay，避免改变既有客户端语义。

## 未保存头文件与包含者覆盖（OVL-04）

当 `documents` 中包含未保存头文件时，Core 通过 `input_aliases` 反向依赖自动查找所有已知包含者（`known_includers`）：

- **受影响包含者失效**：未随本次 overlay 编译更新的其余已知包含者（`stale_includers`）在 SQLite 中被置为 `stale` 状态并推进 `disk_revision`，确保旧磁盘边在项目查询中被彻底抑制，杜绝跨文件读取陈旧语义事实。
- **实际覆盖范围报告**：ticket 及项目响应新增 `includer_coverage` 结构：
  - `scope`：`"none"`（无已知包含者）、`"partial"`（部分包含者已更新）、`"full"`（所有已知包含者均已覆盖）。
  - `known_includers`：受未保存头文件影响的全部已知 TU 列表。
  - `updated_includers`：本次已随内存文本更新的 TU 列表。
  - `stale_includers`：已被失效、待更新的 TU 列表。
- **完整性如实声明**：`completeness` 字段动态反映真实覆盖状态（例如 `"partial includer coverage: 1 of 2 known includer(s) updated in overlay; 1 includer(s) invalidated by unsaved header changes; project not fully updated"`），绝不声称全项目已更新。
- **无包含者边界处理**：未被任何已知 TU 包含的新建/未索引头文件，其 `includer_coverage.scope` 记为 `"none"`；直接请求该头文件预览而未指定宿主 TU 时，明确返回 `no matching TU; header has no known includer records; analyze an including source file first`。

## 多 TU 前台调度与并发控制（OVL-05）

在存在多个受影响编译单元（如头文件变更波及多个已知包含者）时，前台 overlay 调度器执行有界优先级调度：

- **活动文件优先**：主请求文件（活动编辑 TU）始终排在队首，确保用户当前阅读或编辑的单元第一时间开始编译并就绪。
- **后台可让路**：前台 overlay 调度触发时立即调用 `defer_index_for_preview()`，若后台索引进程处于运行态则主动取消，将其未完成单元归还 pending 队列，绝不阻塞前台响应。
- **连续修订合并与有界队列**：
  - 队列最大深度严格限制为 `MAX_QUEUED_OVERLAYS = 16`，超限截断旧项。
  - 用户连续输入产生新修订时，新到达的请求自动使旧运行项与待处理队列失效（`superseded`），合并同一 TU 的工作并替换为最新修订，杜绝旧版本堆积。
- **不扩大到全部未索引单元**：前台队列仅调度主 TU 与经由 `query_store.affected` 识别出的已知包含者，严禁自动扫描或扩展到编译数据库中无关的未索引单元。
- **编译并发严格受预算控制**：全局编译工作进程并发上限为 1，前后台工作进程物理上不重叠；状态中通过 `queued`、`queue_len`、`queued_units` 和 `worker_active` 明确表达当前队列与活跃状态。

## 内存结果原子切换与修订隔离（OVL-06）

在多 TU 前台编译与多修订持续编辑场景下，核心协议保障内存语义结果的原子切换与版本强一致性：

- **修订隔离无混杂**：一次查询（`semantic.preview.at/relations`、`semantic.project.at/relations`）合并的所有 overlay 事实必须严格匹配当前 ticket 的 `documents` 修订集合。即便内存中存在多个 TU 的已编译结果，系统也仅合并输入指纹与当前文档修订集合完全吻合的快照，绝不会将文件 A 的修订 1 与文件 B 的修订 2 混杂返回。
- **迟到结果防回退**：若后台编译工作进程因旧修订或旧 ticket 产生迟到结果，主事件循环通过当前 ticket 的 `job_id`、`epoch` 及输入指纹强制校验；不匹配当前版本的迟到结果直接丢弃，严禁覆盖最新状态或回退当前版本。
- **切换期间明确等待状态**：
  - 在前台编译排队中（`queued`）或运行中（`running`）发起查询时，`semantic.preview.at/relations` 与 `semantic.project.at/relations` 明确返回错误码 `preview_not_ready`，并在错误消息中提示 `preview compilation in progress (state: ...)`。
  - 进度与状态接口在切换期间返回明确的未就绪指示与描述（`"compilation in progress for revision X; results incomplete"`），避免前端读取半成品或产生静默空结果。

## 失败 TU 的合并语义与缺口定位（OVL-07）

在 overlay 编译遭遇错误、超时或内存超预算时，核心协议定义了清晰的隔离、缺口定位与保留语义：

- **旧边绝不重新出现**：
  - 触发 overlay 编译时，主 TU 及其已知包含者在 SQLite 中被先期置为 `stale` 状态。
  - 当 overlay 编译失败（编译错误、超时或内存超预算）时，失败的 TU 绝不会复活或退回其磁盘旧版本。无论进行项目级关系查询（`semantic.project.relations`）还是磁盘关系查询（`semantic.relations`），失败 TU 的旧贡献与旧调用边均被持续遮蔽，杜绝陈旧边重新出现。
- **其他有效 TU 正常保留**：
  - 单个或部分 TU 的编译失败不影响项目中其他未受影响的有效持久化 TU 或其他编译成功的 overlay TU。
  - 其余有效 TU 的声明、定义、引用及调用者在合并查询中完整保留，避免因单文件错误清空全项目语义。
- **失败原因与缺口精确定位**：
  - 状态与项目查询响应中结构化输出 `failed_units` 数组，包含 `unit_id`、`main_file`、`reason`、`kind`（`compile_error`/`timeout`/`budget_exceeded`）以及编译器行/列诊断。
  - `completeness` 字段动态描述当前缺口，明确声明哪些 TU 失败、旧贡献已被遮蔽、有效 TU 已保留，使调用方能够精确感知并定位语义盲区。

## 保存后的基线接续与退役（OVL-08）

当调用 `document.save` 保存缓冲区文本时，协议规范保障持久化基线接续、内存贡献退役与去重：

- **安全保存与摘要确认**：
  - `document.save` 接收 `path` 与 `revision` 参数。若修订版本过时或不符，明确拒绝并返回错误。
  - 写入磁盘后重新读取校验并确认 BLAKE3 摘要。若磁盘写入或摘要校验失败，保留内存缓冲区并**严禁清除 dirty 标记**，杜绝未保存内容静默丢失。
- **基线平滑接续**：
  - 保存成功后移除 dirty 状态，并将确认后的摘要记录为最新磁盘打开基线。
  - 触发持久化引擎重新分析该文件；SQLite 中的单位状态由 `stale` 更新为 `current`，并在同一事务中推进 `disk_revision`，完成基线无缝接续。
- **内存贡献退役与防重复计边**：
  - 保存完成后立即退役对应的内存 overlay 事实（`state: "retired"`，清空结果与内存配额计费）。
  - 在后续的项目关系查询或磁盘关系查询中，事实完全由更新后的 SQLite 磁盘基线提供（`evidence: "clang_semantic"`），已退役的 overlay 不再提供同名边，保证关系与引用**绝不重复计边**。

## 多文档生命周期与状态回收（OVL-09）

在真实编辑与代码阅读过程中，用户频繁在多个文档之间切换、打开、关闭、保存、丢弃或重新加载。协议严格保障多文档生命周期的隔离性与事实回收精确性：

- **查看干净文件不破坏未保存结果**：
  - 调用 `document.open` 打开或切换至未修改的干净文件时，Core 通过 `overlay_affects_path` 严格检测：若目标文件不是当前活跃 ticket 的主文件、不在 `documents` 编译列表内，且不属于相关头文件反向依赖链，则严禁调用 `invalidate_preview`，更不得清除其他文件的 dirty 状态。
  - 用户在阅读或导航其他文件的同时，已就绪的未保存语义预览与项目查询事实保持完全有效和可查询状态。
- **关闭干净文件隔离**：
  - 调用 `document.close` 关闭未修改的干净文件时，仅释放该文档在语法引擎中的句柄，绝不触发对其他脏缓冲区 overlay 事实的误清理。
- **丢弃与重载精确回收**：
  - 当对已处于 dirty 状态的文档重新调用 `document.open` 时，系统判定为用户**丢弃（Discard）**未保存修改并从磁盘**重载（Reload）**。
  - 立即清除该文件的 dirty 标记；若该文件参与了内存 overlay，则精确失效对应的瞬态 ticket（`state: "stale"`），释放内存结果。
  - 自动触发对该文件的基线重新索引，恢复 SQLite 中的磁盘基线（`state: "current"`），使查询立即接续磁盘事实。
- **关闭脏文件回收瞬态贡献**：
  - 调用 `document.close` 关闭处于 dirty 状态的文档时，立即移除 dirty 状态并回收其在内存中的 overlay 贡献，清除等待队列中关联的任务，并同步刷新磁盘索引，杜绝已关闭未保存事实长期滞留内存。
- **工作空间切换与配置修改彻底回收**：
  - 调用 `workspace.open` 切换工作空间时，彻底重置旧工作空间的 semantic 控制器、取消正在运行的 worker 进程并 join 线程、清空全部 dirty 集合与语法引擎缓存，新工作空间从零干净启动。
  - 调用 `semantic.configure` 或底层 `compile_commands.json` 发生外部修改时，旧 Controller 与全部已有 ticket 立即失效，任何携带旧配置指纹的查询请求明确拒绝（`stale_query_version`），新配置无缝接管。

## 合并结果的有界分页与稳定版本契约（OVL-10）

针对大型代码仓库中常见的大引用与多入调用关系（如基础库函数、宏定义或核心结构体被数百上千处调用），协议提供轻量、受预算约束且版本严格绑定的分页机制：

- **统一分页请求参数**：
  - `limit`：单页最大条数，服务端强制截断在 `[1, 1000]` 范围内（缺省为 100）。
  - `offset`：当前分页偏移量（非负整数，缺省为 0）。
  - `query_version`：强类型查询版本。**当 `offset > 0`（即翻页或拉取后续页面）时，必须显式携带上一页返回的完整 `query_version`**；若缺失直接报错拒绝（`missing_query_version`）。
- **杜绝跨页偷换版本（No Cross-Page Version Switching）**：
  - 翻页请求到达时，服务端对请求携带的 `query_version` 与服务端当前状态（包括工作空间根、编译配置指纹、SQLite 事务基线、活动 overlay 文档修订集合及覆盖范围）进行一致性比对。
  - 若在翻页间隔期间工作空间发生保存、编辑、重载或配置变更导致版本不一致，服务端**严禁静默在最新快照上继续拉取并拼装结果**，必须明确拒绝并返回 `stale_query_version`，提示客户端刷新重查。
- **结构化截断与页码信息**：
  - 响应中返回 `limit`、`offset`、`total`（全局符合条件的事实总数）、`has_more`（布尔值，表示是否仍有后续数据）与 `truncated`。
  - 当存在截断时，`truncation_reason` 输出详细原因（例如 `"results truncated at page limit 20; 80 row(s) remain; fetch next page with offset 20"`）。
  - `completeness` 字段动态描述当前窗口与进度（例如 `"showing rows 0..20 of 100; page 1 of 5; ..."` 或末页显示 `"(final page)"`）。
- **按需分层有界拉取，绝不全量加载 TU**：
  - 在底层 SQLite 中，通过 `COUNT(*)` 轻量统计磁盘事实总数，并使用 `LIMIT ? OFFSET ?` 直接在索引层面按需分页读取，避免将全库 TU 快照或大二进制事实反序列化到内存。
  - 在项目级合并查询中，优先由内存中的有效 overlay 事实填充前缀页面；当请求的 `offset` 越过内存覆盖层时，直接向 SQLite 发起精确偏移查询，杜绝二次拉取与内存溢出。

## 项目级 Overlay 黄金用例与规范化口径（OVL-11）

为了确保多文件编辑、宏条件分支、多字节 Unicode 与外部环境波动下语义提取的严密性与长期可维护性，核心协议建立了覆盖六大复杂场景的黄金标准用例与规范化一致性验证口径：

- **多文件修改（Multi-File Edits）**：
  - 支持工作空间中多个头文件与实现文件同时处于未保存 dirty 状态并传入 `documents`。
  - 主编译单元与受影响的已知包含者协同参与调度与合并，调用链与定义解析跨多文件无缝关联。
- **宏条件变体分支（Macro Variants）**：
  - 支持同一共享头文件在不同编译单元中依据不同编译选项（如 `-DFEATURE_VARIANT=1` 与 `-DFEATURE_VARIANT=2`）展开不同分支。
  - 在内存未保存解析时，libclang 严格遵循各 TU 独立的编译命令参数，准确解析各自特定的调用目标与变体符号，不发生跨 TU 宏定义污染。
- **多字节 UTF-8 Unicode 鲁棒性**：
  - 源码文件包含中文注释、多字节 Emoji 或 UTF-8 字符串字面量时，符号范围与调用点的位置偏移（`offset`、`line`、`column`）严格按 UTF-8 字节序精准对齐，绝不发生中文字符截断 panic 或偏移漂移。
- **并发外部变化（Concurrent External Changes）**：
  - 当外部进程修改磁盘文件或改动 `compile_commands.json` 时，`ensure_configuration()` 与输入摘要校验机制在查询时立即识别配置与依赖变化，使过时 ticket 自动置为 `stale`（`"preview dependency/configuration changed"`），携带旧版本的查询请求明确拒绝，杜绝读取陈旧或损坏的编译配置。
- **失败与缺口定位**：
  - 语法错误、未声明符号等失败场景在 SQLite 中持续保持对旧事实的遮蔽，并结构化输出 `failed_units` 与动态 `completeness` 缺口，不影响其他有效单元。
- **保存前后规范化口径完全一致（Normalized Equivalence）**：
  - 在内存中通过 `semantic.project.relations` 查询出的关系集合（由 overlay 与有效磁盘基线合并生成），在经过 `document.save` 落盘并重新分析入库后，通过 `semantic.relations` 查询出的全磁盘关系集合，按规范化口径 `(main_file, caller_name, name, location.offset)` 对比：
  - **两者 100% 精确一致，无一遗漏、无一重复、位置与符号名完全吻合**。这证明内存编译器分析与磁盘持久化分析实现了数学上严格同构的语义闭环。

## 旧预览兼容策略与 Swift 客户端验收（OVL-12）

为了平滑演进并彻底消除未保存编辑期间的语义盲区，核心协议在推进项目级合并查询（`semantic.project.*`）的同时，严格维护单 TU 预览（`semantic.preview.*`）的向后兼容策略，并与 Swift `CoreClient` 达成强类型协议对齐：

- **旧预览与项目级端点的并存与隔离策略**：
  - **旧预览端点（`semantic.preview.at` / `semantic.preview.relations`）**：严格保持单 TU 局部语义隔离。该端点仅返回当前活动 overlay 编译单元内提取的事实（如当前函数内的出调用与局部符号），**绝不自动合并其他有效持久化 TU 的定义或调用者**。这保证了既有只关注当前文件的轻量单文档客户端、测试用例与分析器无需感知多 TU 项目状态，行为完全向前兼容。
  - **项目级端点（`semantic.project.at` / `semantic.project.relations`）**：实现项目全局未保存语义合并。通过精准遮蔽当前活动 TU 及受未保存头文件影响的陈旧包含者（`stale_includers`），合并当前 overlay、次级有效 overlay 以及 SQLite 中未受影响的有效持久化 TU 事实；强制要求携带 `project_query_version`，支持有界分页（`limit` / `offset`）并返回 `includer_coverage` 与 `failed_units`。
- **Ticket 生命周期与旧 Ticket 防误用机制**：
  - Ticket 具备强版本绑定（包含 `job_id`、`path`、`revision`、`unit_id`），不可预测且在进程生命周期内单调递增。
  - **立即失效场景**：
    1. **新编辑覆盖（Superseded）**：发起新的 `semantic.preview.start` 时，旧 ticket 立即失效，旧 worker 进程被主动取消，旧等待队列被清空；
    2. **主动取消（Cancelled）**：调用 `semantic.preview.cancel` 后，ticket 状态置为 `cancelled` 并释放内存事实；
    3. **落盘退役（Retired）**：调用 `document.save` 保存成功后，内存贡献退役（`retired`），后续查询由磁盘基线接续；
    4. **文档关闭与丢弃（Discarded/Closed）**：调用 `document.close` 或通过 `document.open` 重新加载丢弃未保存编辑时，ticket 与内存贡献彻底回收；
    5. **重配置与工作空间切换**：调用 `workspace.open` 或 `semantic.configure` 时，控制器重置，全部历史 ticket 永久作废。
  - **拒绝契约**：任何向 `preview` 或 `project` 端点传递不存在、已过时、已取消、已被 superseded 或修订不符的 `job_id` 的请求，服务端均一律拒绝，明确返回 `obsolete or unknown preview job_id`、`invalid_params` 或 `preview_not_ready`，**严禁旧 ticket 误伤新任务或读取陈旧内存事实**。
- **Swift `CoreClient` 客户端对齐与验收**：
  - Swift 端 `SemanticModels.swift` 完整对齐 `SemanticQueryVersion`、`SemanticQueryCoverage`、`SemanticIncluderCoverage`、`SemanticFailedUnit` 与 `SemanticPreviewDocument` 强类型 DTO，`SemanticRows` 与 `SemanticContext` 支持接收结构化分页与截断字段。
  - `CoreClient.swift` 扩展 `startSemanticPreview(documents:)` 支持多未保存缓冲区传参，新增 `semanticProjectContext`、`semanticProjectCalls` 与 `semanticProjectDefinitions` 支持携带 `queryVersion` 与 `offset` 开展项目级分页查询。
  - 生产 stdio 协议与 Swift `CoreClient` 在查询相同未保存编辑状态时，输出完全一致的符号 ID、跨文件定义跳转（定位至目标文件真实源码坐标）、入调用者列表与覆盖状态。

## 可选流水线诊断

在启动 Core 前设置 `SYMWEFT_PROFILE=1`，可记录 worker 的解析、事实提取、输入验证、流式回复编码/写入，以及 Core 的编码、等待、解码、结果验证和持久化阶段。默认关闭；设置在进程内固定，不改变 provider 身份或持久化事实格式。

索引 job 的可选 `profile` 最多保留最近 64 个 TU 记录，并报告总记录数、截断和 checkpoint 耗时。异步 preview 状态的可选 `profile` 包括 run 和结果验证耗时。客户端应容忍字段缺省/null，不能用诊断数据识别符号或查询版本。

该探针存在可测开销。worker 编码与 writer 调用分开计时，writer 包括缓冲和反压；父进程 child_wait 与 worker 阶段重叠，禁止相加冒充总耗时。进程树资源由外部指定根进程的采样器测量，不能从独立 worker 峰值推导。完整字段、边界、运行入口和实测见 [流水线测量](14-分析流水线测量与进程资源基线.md)。
