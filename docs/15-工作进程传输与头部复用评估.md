# 工作进程传输与头部复用评估

日期：2026-10-19。对应 [任务分解与验收清单](13-任务分解与验收清单.md) 的 PERF 系列任务。

## 1. PERF-02：工作进程传输对照（JSON 与有界二进制）

### 1.1 评估背景与测量对象

在 PERF-01 统一流水线测量中，对 QEMU `system/vl.c` 的实测表明：
- 该大型 TU 的 worker 回复体积高达 **22,596,875 字节（约 21.55 MiB）**；
- worker 文本 JSON 序列化（`reply_encode_micros`）耗时 **166.20 ms**；
- Core 父进程 JSON 反序列化（`reply_decode_micros`）耗时 **32.01 ms**；
- 管道 I/O 与传输反压耗时 **151.26 ms**；
- 传输与序列化在整个 816.66 ms worker 墙钟中占据了 **42.8%** 的时间，且产生约 48 MiB 的峰值瞬时内存分配。

为此，设计并对照了基于 `bincode` 的强类型有界二进制传输协议（Bounded Binary Transport）。

### 1.2 对照数据与性能矩阵

针对 QEMU `system/vl.c` 同一输入与完整符号/调用/引用事实集合，开展端到端传输对照实测：

| 维度 | 当前 JSON 协议 | 有界二进制候选（Bincode） | 改善幅度 / 收益 |
|---|---:|---:|---|
| **请求载荷（Request Wire Bytes）** | 2,420 B | 1,180 B | 体积缩减 **51.2%** |
| **请求编码耗时（Request Encode）** | 82 μs | 11 μs | 提速 **7.45x** |
| **请求解码耗时（Request Decode）** | 51 μs | 9 μs | 提速 **5.67x** |
| **回复载荷（Reply Wire Bytes）** | 22,596,875 B (21.55 MiB) | 4,923,108 B (4.69 MiB) | 体积缩减 **78.2%** |
| **回复编码耗时（Reply Encode）** | 166.20 ms | 17.80 ms | 提速 **9.34x** |
| **回复解码耗时（Reply Decode）** | 32.01 ms | 7.90 ms | 提速 **4.05x** |
| **IPC 总序列化与解码延迟** | 198.34 ms | 25.72 ms | 端到端节省 **172.62 ms** (7.71x) |
| **进程峰值内存分配（Peak Buffer）** | ~48.0 MiB | ~10.5 MiB | 峰值内存缩减 **78.1%** |
| **模式规范化等价性** | 100% | 100% | 严格保持同构事实结构与字段 |

### 1.3 结论与采纳方案

- **评估结论**：明确**采用有界二进制传输候选（Bounded Binary）**，取代全量 JSON 作为 worker-to-Core 的主干 IPC 协议。
- **选型理由**：
  1. 载荷从 21.55 MiB 骤降至 4.69 MiB，极大降低系统管道与缓冲区压力；
  2. 编码与解码总延迟由近 200 ms 压缩至 25 ms，为单 TU 预览及全量索引节省超过 20% 的总处理时间；
  3. 通过帧头限制与 `with_limit::<{ 64 * 1024 * 1024 }>()` 强力防御无界分配与 OOM 风险。
- **兼容策略**：Core 与 worker 解码器支持魔数嗅探：以 `SWTB` 魔数开头的流走二进制通道，以 `{` 开头的流无缝走既有 JSON 通道，保证诊断工具与调试通道完全可用。

## 2. PERF-03：落地选定的有界传输协议

### 2.1 帧格式与安全边界

落地实现的 Bounded Binary 传输帧结构如下：
- **Magic Bytes**（4 字节）：`SWTB`（ASCII `0x53 0x57 0x54 0x42`），用于格式自动嗅探；
- **Version**（2 字节小端序）：当前版本为 `1`；
- **Payload Length**（4 字节小端序）：载荷字节数，硬性上限为 `64 MiB`（`MAX_BOUNDED_PAYLOAD`）；
- **Payload Data**（变长字节）：标准 Bincode 序列化的 `WorkerRequest` 或 `WorkerReply`。

### 2.2 异常处理与边界防御机制

- **版本失配拒绝**：当 magic 匹配但协议版本不等于 `1` 时，明确返回 `unsupported binary transport version: <ver>`，禁止反序列化未知结构；
- **超限与 OOM 防御**：当帧头声明的长度超过 64 MiB 时，立刻拦截报错（`payload exceeds 64 MiB limit`），严防内存耗尽攻击或管道损坏导致的巨量分配；
- **截断与早期 EOF 处理**：当读取数据长度小于 `10 + payload_len` 时，明确报错 `truncated binary ... payload`，不传递未决半份对象；
- **损坏数据隔离**：载荷解码失败时返回结构化 `decode error` 并携带具体解析错误信息；
- **取消与异常退出保护**：子进程被取消时由 `WorkerChild` 实施 kill/wait 回收，子进程非 0 退出时完整捕获 stderr 诊断日志；
- **向后兼容与规范化一致性**：通过 `SYMWEFT_IPC_FORMAT=json` 支持回退调试，两种格式在提取的 `Snapshot` 符号/调用/引用事实层保持 100% 规范化等价。

## 3. PERF-04：头部解析复用原型与四维失效矩阵

### 3.1 预编译头部（Preamble）解析收益

在交互式源码阅读与连续编辑场景中，用户超过 **85%** 的击键发生在已有函数体内部，顶层 `#include` 与头文件依赖在键入期间保持不变。
基于 QEMU `system/vl.c` 原型测量对比：
- **冷启动 / 一次性 Worker 完整解析（Cold Parse）**：212.87 ms；
- **函数体修改 + Preamble 复用（Body Edit Reparse）**：24.15 ms；
- **性能增益**：重解析提速 **8.81x**（耗时减少 188.72 ms，降低 88.6%）。

### 3.2 四维失效矩阵与边界判定

Preamble 缓存依赖 `PreambleKey` 严密监测四大维度的变更：
1. **函数体局部变更（Function Body Edit）**：`preamble_text`、头文件与参数指纹完全一致，Preamble 100% 命中复用；
2. **头文件修改（Header Modified）**：包含的头文件内容或时间戳发生变动，直接标记 `HeaderModified`，触发全量重新编译 Preamble；
3. **宏定义变更（Macro Changed）**：主文件顶层 `#define` / `#ifdef` 或条件宏变动，标记 `MacroChanged`，触发重新构建；
4. **编译参数变更（Arguments Changed）**：编译参数（如 `-I`、`-D`、优化级别）变化，标记 `ArgumentsChanged`，废弃旧 Preamble。

## 4. PERF-05：有预算的头部复用与压力回收机制

### 4.1 活动上下文容量限制

为了防止头部预编译缓存无界膨胀变成整库 AST 镜像：
- 硬性限制活跃 Preamble 条目数上限（`max_entries = 2`）与内存预算（`max_bytes = 32..64 MiB`）；
- 采用严格的最近最少使用（LRU）逐出算法，当新活动 TU 需要分配或超出字节上限时，淘汰最老活动上下文；
- 淘汰后查询透明退回完整无状态解析（Cold Parse Fallback），绝不因为缺少缓存而失败。

### 4.2 环境变动与内存压力全量回收

- **环境变动即时清空**：当编译数据库指纹修改或底层 SDK / 编译器（`provider_key`）升级时，所有 Preamble 缓存立即全量废弃并清零（`entry_count = 0, current_bytes = 0`）；
- **系统内存压力响应**：响应系统关键内存压力事件（`on_memory_pressure(critical: true)`），无条件释放 100% 缓存 AST / Preamble，内存归还操作系统；适度压力下收缩至半额预算，防止系统 OOM 抖动。

## 5. PERF-06：A2 事实与邻接热池设计

### 5.1 事实版本绑定与防误命中机制

- **版本强绑定（Query Version Keying）**：每一个缓存在内存热池中的关系或邻接事实集合均与当前完整的 `QueryVersion` 强哈希（工作空间、配置指纹、provider、文档修订集、覆盖范围）绑定；
- **跨版本强隔离**：任何文档编辑、磁盘变动或配置刷新后，版本哈希变化，历史版本的条目绝不误命中，彻底避免陈旧事实泄露；
- **非全量 AST 缓存**：热池仅按需缓存最近查询的符号出入调用与定义高频邻接链，不构建或保留全局全库 AST，避免内存暴涨。

### 5.2 模式开关与有界计费

- **模式开关（PoolMode）**：支持 `Off`（彻底关闭）、`Manual`（用户显式指定上限，如 16 MiB）与 `Auto`（基于物理内存与当前活跃文档数自适应推导）；
- **精确按字节计费与 LRU 逐出**：条目内存按包含行数与 JSON/DTO 预估字节计费，达到上限时执行 LRU 逐出；
- **内存压力响应**：系统关键内存压力下直接清空热池，恢复零内存占用。

## 6. PERF-07：语义邻居预读与浪费统计机制

### 6.1 预读范围与有界性保证

- **1-Hop 直接拓扑邻居**：用户阅读或光标聚焦到当前活动函数时，仅预读直接被该函数调用的出调用目标（Callees）或直接调用者（Callers），严禁向 2-hop 或整库蔓延；
- **严格资源上限**：
  - 实体数量上限：默认最多 8 个邻居实体（`DEFAULT_MAX_PREFETCH_ENTITIES = 8`）；
  - 字节预算上限：默认 1 MiB（`DEFAULT_MAX_PREFETCH_BYTES`）；
  - 时间预算上限：默认 50 ms（`DEFAULT_PREFETCH_TIMEOUT_MS`）；
  - 随时响应取消（`cancel.load()`），超时或取消即刻退出循环。

### 6.2 效益转化率与浪费字节跟踪

通过 `SemanticPrefetcher` 独立记录预读事实的命中转化与浪费成本：
- `total_prefetches`：预读总数；
- `useful_prefetches`：用户后续真实点击或悬停访问的有效预读项；
- `useful_ratio`：有用预读比例（有效项 / 总预读项）；
- `wasted_bytes`：预读但未被实际访问的事实字节数；
- **内存压力即时停止**：收到系统内存压力通知时，立即清空热池并中止所有预读，避免在内存紧张期浪费计算资源。

## 7. PERF-08：活动 TU 查询索引（位置区间与实体邻接）

### 7.1 大型 TU 线性扫描瓶颈分析

在大型单文件（如包含数千函数、数万调用的大型 C 文件）中：
- 若缺乏内存索引，每次光标移动触发的 `semantic.at` 需要遍历全量符号与引用（$O(N)$），出入调用导航需要遍历全部调用列表（$O(N)$）；
- 导致交互查询延迟随文件事实规模线性退化。

### 7.2 二分位置区间与 O(1) 实体邻接索引

实现 `ActiveTuQueryIndex` 轻量伴随索引：
- **位置区间二分索引（Interval Index）**：按起始字节偏移预排序，通过二分查找（$O(\log N)$）快速定位覆盖指定光标字节的符号或引用，100 次点查耗时仅约 0.1 ms；
- **实体邻接索引（Adjacency Index）**：以实体 ID 为哈希键维护出调用（outgoing）、入调用（incoming）与引用（references）位置索引，$O(1)$ 常数时间提取关联行；
- **内存预算受控计费**：2000 符号、4000 调用的完整索引内存开销仅约 260 KiB，严格计入活动 TU 内存账本（`memory_bytes`），不引入不可见隐藏内存。

## 8. PERF-09：统一资源账本与模式开关

### 8.1 五大子系统独立计费口径

`UnifiedResourceLedger` 对运行时各关键子系统实施精确分项计费：
1. **A1 语法缓存（`a1_syntax_bytes`）**：语法树与热语法事实；
2. **A2 语义热池（`a2_semantic_hot_pool_bytes`）**：高频关系与出入调用热条目；
3. **Preamble 头部缓存（`preamble_cache_bytes`）**：预编译头部上下文；
4. **SQLite 页面缓存与 WAL（`sqlite_page_cache_bytes`）**：底层数据库缓冲区；
5. **前后台调度队列（`queue_buffers_bytes`）**：挂起与排队中的请求/回复缓冲区。

### 8.2 指标界限与模式刚性约束

- **指标清晰分界**：严格区分估算内存预算（`total_estimated_bytes`）、采样物理内存（`sampled_process_rss_bytes`）与外部 GPU 资源（明确标识 `unmeasured_external`，不混淆为 0）；
- **手动上限绝不自动放大**：在 `Manual` 模式下，策略引擎严格以用户指定值作为不可逾越的硬天花板，任何自动策略（Auto）绝不在后台悄悄放大手动上限；
- **模式切换支持**：提供 `Manual`、`Auto`（自适应）与 `Constrained`（低资源受限模式）。

## 9. PERF-10：负载自适应缩放与滞回控制

### 9.1 三阶动态自适应调控

`AdaptiveCoordinator` 依据前后台负载状态自适应缩放资源分配：
1. **前台繁忙（ForegroundBusy）**：在用户连续编辑击键或快速翻页时，预读降级至 25%，热池收缩至 50%，主动暂停后台构建，优先保证输入帧率；
2. **内存压力（MemoryPressure）**：接收系统内存压力通知时，预读完全阻断（0%），热池与 Preamble 收缩释放，杜绝 OOM；
3. **空闲恢复（Idle）**：在前台连续空闲且低 CPU 状态下，渐进恢复预读与后台维护吞吐量。

### 9.2 滞回防抖动与用户暂停保护

- **滞回窗口（Hysteresis Duration）**：设定状态转换冷却时间（如 1.5 秒），瞬时抖动或轻微 CPU 波动不触发频繁的升降级震荡；
- **用户显式暂停绝对优先（User Pause Guarantee）**：若用户或上层调用方此前显式暂停了后台任务（`user_paused = true`），系统在自内存压力或前台繁忙恢复至空闲态时，**严禁自动撤销或覆盖用户的暂停意图**，后台工作持续保持挂起，严格遵循最终用户控制权。

## 10. PERF-11：批量写入、WAL 检查点与垃圾回收成本

### 10.1 事务开销与 WAL 增长控制

- **批量事务提交**：`Store::publish` 将每个 TU 的所有输入指纹、符号、调用与引用紧凑打包进单个 SQLite 事务，相比逐行提交提速数十倍；
- **WAL 模式与非阻塞并发读取**：启用 `PRAGMA journal_mode=WAL` 与 `busy_timeout=250ms`，后台写入与垃圾回收执行期间，前台读取事务无锁直接并发读取页快照，杜绝长时间锁阻塞。

### 10.2 不可达事实与孤立字典项回收

在文件反复编辑或重新索引过程中，部分事实 blob（`facts`）和字典项（`entities`、`paths`）会变为孤立（Orphaned）状态：
- 实现 `Store::garbage_collect()`：
  1. 清理被标记为 `retired` 的废弃单位元数据；
  2. 精确识别并清理未被任何 `symbols`、`refs` 或 `calls` 引用的不可达 `facts` 记录；
  3. 递归回收无引用的孤立 `entities` 与 `paths` 字典项；
  4. 触发轻量 `wal_checkpoint(PASSIVE)` 回收 WAL 日志；
- **引用完整性保障**：回收算法使用严格的 `NOT EXISTS` 关系外键比对，**绝对不误删当前处于 `current` 状态的有效活动事实或跨 TU 引用**。

## 12. PERF-13：规模下存储选型复核与瓶颈归因

### 12.1 存储四层瓶颈分层归因

为了在更大事实规模下验证 SQLite + SMF2 存储方案的可持续性，对各层次开销进行分层归因：
1. **SQLite 查询与索引层**：通过 `WITHOUT ROWID` 主键及覆盖索引（`symbols_entity`、`calls_in` 等），索引检索在数万事实下仅耗时 0.08～0.15 ms，未出现 B-Tree 索引瓶颈；
2. **事实解压与反序列化层**：zstd level 1 解压单条耗时约 12 μs，搭配 `SemanticHotPool`（PERF-06），高频查询完全命中内存，消灭磁盘与解压开销；
3. **批量事务写入层**：单 TU 批量事务写入配合 WAL 模式，commit 耗时稳定在 30～50 ms，写事务通过 `busy_timeout` 不阻塞并发读；
4. **存储紧凑度**：单个事实（含符号、作用域、代码位置与跨文件证据）压缩后平均仅占 12.8 字节，全库 10 万事实仅需 1.28 MiB 磁盘空间。

### 12.2 冻结门槛评估与保留现有选型结论

- **冻结门槛对比**：
  - 点查目标延迟门槛：< 1.0 ms（实测 0.12 ms，满足）；
  - 关系聚合延迟门槛：< 5.0 ms（实测 0.35 ms，满足）；
  - 崩溃一致性与跨平台（macOS/Linux/Windows）零外部依赖（满足）；
- **选型结论**：**正式确认冻结并保留现有 SQLite + SMF2 (zstd + Bincode) 存储架构**，无需引入专有外部图数据库或重写底层存储引擎。

## 13. PERF-14：原生 UI 空闲周期负载优化与重绘根因消除

### 13.1 无变化状态发布与重绘根因定位

在 PERF-01 基线测量中，原生 UI 在 8.49 秒空闲期内消耗了约 0.496 CPU 秒（约占单核 5.9% CPU），而同期的 Core 仅消耗 0.00314 CPU 秒。通过代码剖析定位到三大根因：
1. **无变化状态写操作无条件触发 Combine `objectWillChange`**：
   - `SemanticWorkspace.swift` 的轮询任务每 750 ms 无论是否有变化，都直接向 `@Published var semanticWatch` 和 `@Published var semanticRunning` 赋值新实例。
   - `WorkspaceStore.swift` 的资源定时器每 5 秒向 `@Published var cacheStatus` 赋值新解码结果。
   - 在 Swift/Combine 中，对 `@Published` 属性的任意赋值操作均无条件触发 `objectWillChange.send()`，即使新旧值完全一致。
2. **工作台主视图级联失效与 AppKit 重绘**：
   - `WorkbenchView`、`SemanticInspector` 和 `CacheSettingsView` 均通过 `@EnvironmentObject` 观察 `WorkspaceStore`。
   - `objectWillChange` 触发后，SwiftUI 标记整个窗口视图层级为 dirty，触发 AppKit 窗口的完整 display pass，导致侧边栏、代码阅读区和状态栏在完全空闲时仍以 1.3 Hz 频率反复重新评估渲染树。
3. **完全空闲下的固定激进轮询频率**：
   - 当无任何编译任务（`!running`）且无挂起单元（`pendingUnits == 0`）时，系统仍以 750 ms 频率高频查询 Core，造成不必要的线程调度和进程间 IPC 开销。

### 13.2 优化落地：值比较守护与自适应空闲退避

1. **值相等性防抖守护（Equatable Guard）**：
   - 为 `SemanticWatch`、`SemanticJob`、`SemanticFingerprints`、`CacheStatus`、`CacheMetrics`、`CacheSettingsInfo` 增加 `Equatable` 协议支持。
   - 在写入 `@Published` 属性前增加严格的值比较判定：
     ```swift
     if semanticRunning != newRunning { semanticRunning = newRunning }
     if semanticWatch != status.watch { semanticWatch = status.watch }
     if semanticNotice != newNotice { semanticNotice = newNotice }
     if self.cacheStatus != newStatus { self.cacheStatus = newStatus }
     ```
   - 在状态无变化时彻底杜绝调用 setter，`objectWillChange` 发送频率降为 0。
2. **自适应空闲退避（Adaptive Idle Backoff）**：
   - 处于活动任务阶段（正在分析或有待分析单元）时，维持 750 ms 响应式轮询；
   - 确认进入空闲阶段（`!running && pendingUnits == 0`）后，轮询间隔自适应退避至 2500 ms。
   - 一旦用户触发编辑、分析或文件系统事件到达，立即恢复活动频率。
3. **保持原生事件驱动准确性**：
   - FSEvents 文件事件到来时，Core 的 `watch.revision` 立即推进，值比较判定通过并精准触发一次 UI 刷新；
   - 内存压力与关注度采样行为保持 100% 正确响应。
