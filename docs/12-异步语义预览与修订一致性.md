# 异步语义预览与修订一致性

日期：2026-10-18。承接 [C/C++ 语义闭环](10-C-Cpp语义闭环与QEMU验证.md) 和 [实时维护](11-实时语义更新与查询优化.md)。本阶段重点是未保存内容的真实编译器关系，以及编译期间的交互响应。

## 1. 已实现的变化

此前 `semantic.preview` 会同步等待 libclang，耗时较大的 TU 会占住 stdio 请求循环。本阶段增加异步预览生命周期，兼容保留旧方法。新的客户端应使用 `semantic.preview.start/progress/at/relations/cancel`。

- 启动请求只选择 TU、登记修订和排队；编译、提取、输入复核在后台执行。
- 前台预览与磁盘索引共用一个编译工作进程名额。预览会请求取消当前索引，将预算内未完成范围留待后续维护；确认旧工作线程退出后才启动新预览。
- 同时最多一个运行请求、一个待启动请求、一个已完成结果。新请求替换等待项，取消运行项，并立即释放旧结果；连续请求不会积累历史快照。
- 预览提供位置查询、声明/定义、引用、出入调用，不必在每次轮询中传输整份 TU 快照。
- 预览不调用 Store.publish，不保存未提交的事实或源码；主索引继续表达磁盘状态。
- 当前只支持一个未保存缓冲区参与预览；另有 dirty 文档时显式拒绝，避免将其他未保存内容错误地当成磁盘版本。

macOS CoreClient 和 DTO 已接入新协议，并通过真实 Rust 子进程验证。**当前应用的阅读器仍为只读，尚未提供用户编辑、保存、冲突处理和自动发起预览的界面。** 本阶段完成的是编辑器所需的分析后端和客户端接口。

## 2. 调度和状态

```text
document.edit → A1 增量语法事实立即可用，相关 A2 磁盘贡献失效
                        ↓
preview.start(path, revision, unit_id?)
                        ↓
queued → 请求旧工作取消 → 旧线程已退出 → running
                                           ↓
                  编译 / 提取 / 输入与预算复核
                                           ↓
                                     ready / failed
                                           ↓
                          preview.at / preview.relations
```

任意阶段都可能因下一次编辑、文件打开/重载/关闭、配置变化、源文件事件、客户端取消或 critical 内存压力进入 stale/cancelled。过期与取消都立即释放可查询结果；`worker_active` 可能短暂为 true，表示取消中的工作进程尚待回收，不能据此重新并发启动一个编译器。

任务由语义请求推进；纯 serve 客户端仍需轮询。没有额外定时器、每个按键一个线程或常驻全库 AST。主应用已有 750 ms 磁盘维护轮询；未来前台编辑预览宜独立采用约 180–300 ms 防抖，并在用户继续输入时取消旧请求。该时长是交互建议，尚非 UI 已实现行为。

磁盘自动维护保留既有 256 TU 上限；抢占超过该范围的批量工作会进入显式刷新状态，不把庞大批量任务无条件塞回自动队列。用户原先的暂停状态不会被预览撤销。

## 3. 修订和身份保护

每个请求返回 ticket：`job_id/path/revision/unit_id`。内部另记录缓冲区 BLAKE3 摘要和结构事件 epoch。

1. Core 先检查 Engine 中的 path/revision，拒绝已被后续编辑替代的源文本。
2. job_id 在同一个 Core 进程生命周期内全局递增，重新导入配置、切换工作空间也不重用，防止迟到的取消误伤新任务。
3. 新请求立即替换当前 ticket。旧线程即使成功结束，也只能被回收，不能覆盖当前结果。
4. 结果就绪前检查 provider、unit_id、command_key、configuration、编译数据库和响应文件；overlay 输入必须与请求摘要一致，其他实际加载输入必须仍与磁盘一致。
5. 读取时再次验证 ticket、当前 Engine 修订、配置、结构 epoch 和已加载依赖。已启用健康监听时复用有时限的输入指纹；关闭缓存时严格读取。
6. cancel 必须携带 job_id；旧 ticket 的取消返回错误，不影响新请求。通用 `semantic.cancel` 仍取消全部当前语义工作并暂停自动维护。

同一文件的多编译变体、头文件的多个包含者均要求显式 unit_id，不能默认选择第一个。首次尚未索引的头文件没有包含者记录时，仍需先分析相应主文件。

严格指纹验证针对已加载输入，并非整个文件系统的原子快照。新增同名头文件、include 搜索路径结构变化还依赖原生结构事件；未开启监听时，不能仅凭已加载文件摘要证明搜索结果从未改变。运行中尚无完整依赖集合，因此源文件/构建相关事件采用保守失效；结果已完成后也可能因结构事件重新分析。

## 4. 查询语义与覆盖范围

查询证据标记为 `clang_semantic_overlay`，行包含 `evidence`、`freshness=overlay`、revision、preview_id、unit_id、main_file。位置依旧使用 UTF-8 字节区间；Core 拒绝落在多字节字符中间或缓冲区外的查询。

`preview.at` 返回 references/declarations/enclosing_functions，只有候选唯一时才返回 entity_id。`preview.relations` 支持 definitions/declarations/references/incoming/outgoing，默认 100、上限 1000；每类位置候选上限 32。

**这些旧 preview 查询只覆盖当前预览 TU。** 其加载的项目头文件也可包含在事实中，但其他 TU 的定义、调用者不会自动并入。例：当前 C++ TU 预览绑定到另一个 C 文件定义的函数，如果只有头文件声明，overlay definitions 返回空仍是正确结果。

2026-10-19 增补：`semantic.project.at/relations` 已实现单 overlay TU 的项目级合并。该路径先排除当前 ticket 的精确 unit_id 旧磁盘贡献，再合并当前内存贡献及其他通过自身输入校验的磁盘 TU；声明/定义/引用/出入调用保留逐行证据、变体和来源，项目覆盖使用独立的 `project_query_version`。未就绪或失败不会重新暴露旧边；多缓冲区、原子多结果切换和稳定分页仍属后续任务。

虚调用候选、间接/未解析目标沿用已有证据语义。没有将名称相同当成实际绑定；当前也没有因此获得完整 C++ 模板、隐式构造/析构、动态派发或跨项目准确性。

## 5. 资源预算与取舍

| 项目 | 当前约束 |
|---|---|
| 缓冲区源码 | 单个 overlay，最大 8 MiB；Core 文档预算仍先行生效 |
| 待启动项 | 仅最新一个，替换时释放旧源码 |
| 编译并发 | 索引和异步/旧同步预览合计最多一个 |
| 工作进程 | 默认 30 秒、512 MiB 采样 RSS 软预算，沿用既有限制 |
| 已完成结果 | 仅一份；默认 32 MiB，可在 start 中指定 memory_mib=1..128 |
| 结果计费 | Vec 容量 × 元素大小，加 String 容量；包括依赖、符号、引用、调用和诊断 |
| 超预算 | 丢弃完整结果，返回 failed，charged_bytes=0；不提供被截断后貌似完整的关系图 |
| 压力 | critical 取消、清空结果并拒绝启动；normal/warning 后可重新请求 |
| 轮询传输 | 不含完整 snapshot；原因最多 2048 字符、诊断最多 64 项且每条消息最多 1024 字符 |

该配额是**保留结果的容量计费**，不等于 malloc 实际大小或整个 Core RSS。metadata、分配器开销、运行中请求、JSON 管道缓冲和反序列化峰值另计。结果超过预算只能在接收、反序列化并测量后拒绝；取消后逻辑数据释放，分配器不保证立即归还 RSS。工作进程 64 MiB 输出限制也不是 Core 峰值限制。

本方案没有新增数据库，也不需要另造持久化文件格式。SQLite/SMF2 继续保存稳定磁盘事实；瞬时修订留在单槽内存，避免按键级 WAL 写入、GC 和重启恢复复杂度。代价是当前每次预览重新建立 TU，无法复用 preamble/AST。

优先级判断：本轮首先解决阻塞、取消和错修订问题；要继续缩短大型 TU 的编译时间，应评估有预算的 preamble/有限活动 TU 复用；要压低 Core 峰值，应优先测试有界二进制工作进程传输及分配复用。不能把元数据缓存的毫秒级读取当成每次重新编译的性能。

## 6. QEMU 实测

Apple M2 / 16 GiB、macOS 26.6.2，release Core、libclang 21。使用此前真实 QEMU aarch64-softmmu 配置（2855 命令）的同一 30 TU 持久化子集副本，保持相同 CPATH/SDKROOT；不重新执行全库编译。

测试只对 `system/vl.c` 的内存末尾追加注释，以验证真实大型 TU 预览路径，不修改 QEMU 源码。启用原生监听和指纹缓存、关闭自动磁盘重建；OS 页面缓存已热。调用边替换正确性另由小型跨 C/C++ 样例验证。分析期间重复读取 `system/main.c`，预览完成后各执行 30 次位置和出调用查询。

| 指标 | 本机本轮结果 |
|---|---:|
| start 确认，包含 stdio | 2.90 ms |
| ready，总墙钟（含轮询） | 774.48 ms |
| 后台工作总耗时（含传输/复核） | 741 ms |
| libclang parse / 事实提取 | 287.59 / 294.70 ms |
| 编译期间源码读取，24 样本 p50 / p95 / max | 0.24 / 0.62 / 0.94 ms |
| overlay 位置查询 p50 / p95 | 2.36 / 3.32 ms |
| 405 项出调用查询 p50 / p95 | 4.75 / 5.56 ms |
| 保留事实容量计费 | 24,773,188 B，约 23.63 MiB |
| Core 采样 RSS 范围 | 73.34–125.41 MiB |

RSS 来自父 Core 的离散 ps 样本，包含 A1 文档、已有查询连接、监听器、overlay 和传输分配；不是准确峰值，不包含同一时刻工作进程总量。不能将该范围和旧报告的 worker 最大值相加当作同时进程树峰值。没有把约 774 ms 宣称为增量编译或全库分析时间。

实际验证 qemu_init 仍有 405 项出调用；取消后 charged_bytes=0，磁盘文件逐字节相同，preview 前后的持久化索引状态一致。基准脚本复制 SQLite 的逻辑备份，避免污染此前读取基线的 current/stale 状态。

复现：`python3 scripts/benchmark-qemu-preview.py`。需要既有 QEMU 构建配置和 `build/semantic/qemu-realtime/cache` 基线，并保持基线记录的编译器环境；脚本不会重新引导 QEMU 构建环境。原始数据见 [JSON](12-preview-benchmark.json)，本机完整产物位于 `build/semantic/qemu-preview/preview.json`。

## 7. 验证与后续

- Rust 调度集成测试使用持有 OS 文件锁的假编译器，检查真实进程不重叠、索引被抢占、最新等待项合并、旧 ticket 取消隔离、超预算结果拒绝。
- 生产 stdio 测试使用真实 libclang，验证 UTF-8、first → second 绑定、所有关系方向、旧修订拒绝、依赖失效、关闭/取消/压力回收、重新配置后 job_id 不重用以及真实原生文件事件。
- Swift 检查使用生产 CoreClient 和 DTO，实际执行内存编辑、异步启动/轮询、上下文/出调用和取消，确认磁盘源码未变。
- 原有磁盘语义、文件事件、缓存、A1 测试继续作为回归；32 项 Rust 测试、clippy、生产语义/监听/预览协议、Swift foundation 均通过。macOS 发布应用已重新构建并完成浅色/深色外部保存回归。

## 8. 交给 Claude Design / Google Stitch 的增量要点

以下用于后续可编辑界面设计，不表示本轮已实现 UI。

- 系统浅色/深色主题自动跟随，代码底色继续使用较轻的原生中性色。
- 未保存文件以原生状态点标识；语法大纲立即更新，语义面板显示排队、分析中、当前修订就绪、过期、取消或编译失败。
- 新修订开始后立即收起旧的准确关系；等待时可以继续显示明确标为“语法候选”的信息。
- 语义面板明确“当前未保存 TU”覆盖范围及编译变体；项目级磁盘结果另有证据标签，不能混成一个貌似完整的调用总数。
- 提供轻量取消入口和保留结果内存上限；预算不足提示调整预算或缩小分析范围，不出现空图却宣称分析完成。
- 外部保存与本地未保存缓冲区冲突时保留用户内容，给出比较/重载/保留操作；不能复用当前只读模式的自动重载行为。
