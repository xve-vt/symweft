# 大规模索引、预读与双维热度评估

2026-10-18。状态：QEMU 基线、四种存储形态对比、A1 持久化与缓存已完成本轮实现和测量。实测见 [QEMU 性能与存储选型报告](09-QEMU性能与存储选型报告.md)。以下是方案评估及目标约束，已实现范围在文末单独列明。

## 1. 必要性、收益与代价

| 能力 | 必要性与收益 | 风险/代价 | 决策 |
|---|---|---|---|
| 持久化与按需加载 | 必需，重启无需全库重分析，内存不随仓库等比例增长 | 版本、依赖失效、崩溃一致性与迁移 | 本轮实现 A1，A2 保留独立精度边界 |
| 按字节计费的热缓存 | 必需，少量巨型文件不能挤占全部资源 | 估算不是 RSS，外部引用与解析峰值另计 | 缓存计费、进程峰值、磁盘页缓存分别报告 |
| 动态预算与手动模式 | 必需，多应用并存、笔记本和小内存机器需求不同 | 抖动、增长过快、和系统缓存竞争 | 有上/下限、压力时快速缩减、恢复时渐增；提供开关和手动上限 |
| 按需预读 | 有价值，可降低下一跳等待 | 错误预测浪费 I/O、污染缓存、索引过期 | 低优先级、小配额、只读已有索引；压力下停用；前台命中仍校验指纹 |
| 两类热度 | 有价值，架构热点与个人关注不是同一个概念 | 合并后无法解释，历史计数会固化旧热点 | 分开保存/输出；缓存内部可以受限地组合 |
| 自定义磁盘格式 | 有条件可行，定长目录/连续事实块可能降低读取成本 | 崩溃恢复、校验、GC、并发、版本兼容与二级索引都要维护 | 与 SQLite 做同数据对比，收益显著才替换；先作为实验后端 |

## 2. 存储选型不预设 SQLite 获胜

同一份分析事实、相同编码、相同文件顺序下对比：

1. SQLite：按路径与内容指纹定位紧凑快照，关系/名称索引以正常表保存。
2. 二进制分段包：按偏移读取连续事实块，独立目录记录路径、内容指纹、偏移、长度、校验与格式版本。
3. 混合：事实块使用分段包，事务元数据、关系、热度与更新清单由 SQLite 管理。

完整比较首次构建、重启目录加载、随机读取的原始字节/解码耗时、热命中、局部更新/写入放大、最终体积、RSS、索引覆盖与失败。不能将只支持 get 的文件包，与提供反向关系/事务/排名的完整数据库直接比较后宣称全面替代。

系统页缓存不主动清空，不使用需要管理员权限的 purge。报告明确是“新进程/应用缓存空，但 OS 页缓存可能已热”；真正物理冷盘需要独立受控环境。读速分别测原始 payload、解码、内容校验和端到端，不混为一次数字。

自定义格式至少具备 magic/version、固定字节序、长度上限、内容校验和原子目录发布。写段先持久化，再提交引用；崩溃留下的无引用尾部可回收，不能让目录指向未写完整数据。压缩、mmap 和多线程均经测量后启用，不能默认一定更快。

SQLite 使用固定的已修复版本、WAL、短事务、受限页缓存和批次；测量后决定采用数据库或混合。WAL 的单写者、checkpoint 和版本要求遵循[官方说明](https://www.sqlite.org/wal.html)。

## 3. 缓存策略与扫描隔离

分开管理不可丢弃的活动文档/编辑状态、可回收的语法树、可回收的解码事实与邻接页。全量扫描流式处理，**不将每个扫描文件提升为用户热项**，也不保留全库 AST。

纯 LRU 简单，但全量扫描会挤掉用户正在反复阅读的文件；纯 LFU 容易固化历史。成熟的频率准入与分段策略可改善扫描污染，但需要额外元数据与维护。[Caffeine 原始设计参考](https://github.com/ben-manes/caffeine/wiki/Design)

本轮优先实现可解释、按字节计费的分段/频率缓存：一次访问进入试用区，重复需求访问进入保护区，预读位于可先淘汰区；元数据有界，旧频率衰减。结构先验权重受限，不能让基础工具函数长期独占缓存。不得称作完整 W-TinyLFU，除非实际实现相应准入/频率草图并通过验证。

缓存命中不仅更新计数，还记录有效读取的延迟与字节收益。淘汰优先考虑未使用预读、低频、久未访问和较低单位字节收益。活动编辑内容不因缓存缩减而丢失，必要时只释放 AST/可重建事实。

## 4. 两种热度的定义与输出

### 结构热度

准确语义可用后分别保存：静态调用位置数、独立调用者数、跨文件/模块调用者数、fan-in、fan-out，以及证据和构建变体。它表示静态代码关系，不等于运行时调用频率；结构指标随索引 generation 更新，不采用用户使用时间衰减。

当前 QEMU 测试只有 A1。可输出显式调用点数量及简单名字的语法提及候选，但**不能将全库同名计数称作已解析入调用**。重复名称、宏、函数指针与条件编译导致歧义，必须输出 proxy/ambiguous 标记，真实 resolved_incoming 保持 unknown。文件指标应说明是本文件调用点还是候选被引用数，避免混淆。

### 用户行为热度

分别保存打开/主动跳转次数、有效前台停留时长、最近访问、衰减关注分数与手动关注状态。文件和符号各自记录；符号采用可说明稳定范围的身份，不能仅用行号或函数裸名。

只在应用激活、工作窗口可见、文档可见且未进入长时间空闲时累计时间。按短心跳分段、限制单次上报时间；切换文件/符号时结束上一段。预读、全量分析、后台刷新、自动测试和程序启动默认打开文件都不伪装成用户关注。父/子符号不能将同一停留时间重复计入多个排名项。

用户热度是本地数据，可关闭收集、清空、导出；默认不上传。采用近期衰减，例如 7 天半衰期，但原始累计时长与次数独立保存。缓存访问频率与“用户有效阅读时长”也应分开。

### 对用户展示

文件和符号均提供两个独立排序/列：**结构热度**与**阅读关注**。展示原始指标、时间窗口、快照/变体和精度，归一化分数仅辅助排序；不把两者相加后只给一个不可解释的“热度 87”。

支持 JSON/CSV 导出：path、entity_key、name、kind、structural_metric、structural_value、evidence_level、ambiguous、active_ms、open_count、attention_score、last_seen。图谱可切换“结构/阅读”配色，缺失数据使用 unknown；行为数据为 0 不代表函数没有价值。

## 5. 预算与预读控制

自动模式在用户上限内调整：系统内存告警/严重压力时快速缩小并停止预读，CPU/I/O 繁忙时暂停推测工作；压力解除后有冷却期，结合需求未命中逐步增长。只知道物理内存总量不足以判断可用资源。

手动模式提供缓存开关、最大 MiB、预读开关。上限是应用可回收缓存的目标，不是整个进程 RSS 保证；当前文档、解析临时对象、SQLite 页缓存、索引目录、UI 和语言服务都需要单独报告。严重压力仍允许紧急回收，并显示实际生效预算，不能悄悄声称手动值仍生效。

预读候选依次来自当前文件的已知本地依赖、明确跳转邻居和真实导航历史；同名候选仅作低可信推测。首版仅载入已存在的事实块，不为一次预读启动编译器或全库分析。限制每次候选数、字节、并发和总推测缓存比例；前台请求可在候选之间抢占，切换上下文取消过期计划。

记录预读使用率、浪费字节、前台 p95、命中率和额外 I/O。开启预读如果只增加命中率却恶化前台 p95，也不能算优化成功。

## 6. QEMU 验收边界

本机样本：QEMU VERSION=11.1.1，commit=2df3db357e2d59b7e56c8fa9b97cd035e67d473b。初始盘点当前支持扩展名为 6,723 文件、65,000,505 字节；包含源码树中的测试/第三方源，不跟随子模块下载或运行构建脚本。无 compile_commands.json，本轮不是编译环境语义分析。

先跑原始交互预算引擎，完整记录失败和超限；随后流式全库分析使用明确的批处理预算，不用跳过大文件提高成功率。记录语法不完整文件，宏/片段上下文不会因为“成功生成 Tree”自动变为准确语义。

真实用户导航日志尚不存在。因此局部性/扫描/热点混合访问只能标为 synthetic replay，不能伪造“真实关注”或宣称预测用户行为。预读 A/B 使用相同请求顺序、缓存上限和后端；后台扫描不影响行为热度。

本次 QEMU 约 65 MB 源文件，适合第一轮真实样本，但不代表千万/亿级事实的极限规模已验证。后续仍需更大仓库、多项目、离线变更、长时间运行与压力测试。

## 7. 本轮落地范围与调整

实际首版使用**有限候选采样的频率/字节淘汰**，没有实现前文候选方案的独立试用/保护双队列，也不称作 W-TinyLFU。最近访问票据有界，每次从最多 16 个候选中选择；未用预读得分最低，需求频率随逻辑访问次数衰减，结构与个人关注仅提供受限先验，分数除以字节数平方根避免大对象挤占。语义热点未建立前，这个先验只作弱提示。

默认上限 64 MiB，auto 初始生效 32 MiB，其中 60% 为已解码事实池；SQLite 页缓存约取生效预算的 10%，最小 256 KiB、最大 16 MiB。其余为元数据/短时操作余量，**这些分配不是统一硬内存分配器**。字节池不包含尚被活动引擎引用的事实、源码/AST、队列、语言服务、UI 或系统页缓存；统计不能直接相加为 RSS。批处理仅保留一个分析文档。

压力 warning/critical 将生效预算限制为用户上限的 1/4、1/8，暂停预读；自动恢复需至少 30 秒且出现需求未命中，再按 12.5% 逐步增长。manual 在正常状态恢复手动上限，压力时仍紧急缩减。关闭时清空附加事实池，SQLite 保留最小页缓存，活动文档继续可用。当前 CPU 繁忙信号来自 macOS load average，尚无独立 I/O 饱和度采样；macOS 内存压力由 DispatchSource 提供，界面每 5 秒将状态送入核心。

预读首版仅限已索引、根目录内的本地引号 include；候选最多 4 个、每块不超过 256 KiB，未用推测事实合计不超过事实池的 10%。不解析源码、不启动语言服务，前台命中时重新校验当前源码 hash；跨文件依赖本身是否变化仍须打开校验。新文件请求取消旧计划，在候选之间让前台优先，已经开始的一次 SQLite 读取不会中途取消。

真实阅读关注按约 5 秒采样，仅在前台、可见、源码持有焦点且最近 30 秒内有交互时记录，单次上限 5 秒；一个最内层符号和文件各记一次，不累计到所有父符号。切换边界存在最多一个采样间隔的归因误差，尚不是逐事件精确停留计时。分数为 `previous × 2^(-elapsed/7days) + active_seconds + 2×opened`，原始时间与打开次数另存。可在设置关闭采集/清空当前项目；后台扫描、预读、诊断模式及 synthetic replay 不记关注。手动星标、路径重命名后的语义身份迁移仍在后续范围。

必要性评估保持：持久化、字节预算和动态控制属于基础能力；高级频率策略、预读属于需实测收益的优化。QEMU 合成回放只显示温和的命中改进，同时存在 CPU/额外读取代价，因此后续应以真实导航的等待时间和单位资源收益决定策略，不能只追命中率。
