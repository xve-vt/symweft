# Symweft 分析引擎与实时关系设计

版本：v0.1，2026-10-18。此文是对总体设计的优先级修订；发生冲突时，本文件中用户确认的分析优先约束优先。

最新补充：已实现 A1 持久化、跨重启免 AST 恢复、缓存预算与显式全量命令；进一步落地 C/C++ 首版 A2：编译配置、libclang 绑定、定义/引用/出入调用、后台单工作进程、TU 事务更新、依赖失效与不落盘 overlay 预览。实际能力和 QEMU 30 TU 子集结果见 [语义闭环报告](10-C-Cpp语义闭环与QEMU验证.md)，A1 历史实测见 [存储报告](09-QEMU性能与存储选型报告.md)。本文件主体保留目标架构；完整连续编辑语义、文件监听、跨项目及其他语言 A2 仍未完成。

## 1. 产品中心与工程边界

后续落地：原生文件监听、已索引范围自动重建、持久查询连接和有界指纹缓存已完成首轮验证，见 [实时更新报告](11-实时语义更新与查询优化.md)。本文件涉及尚未完成的“文件监听”描述属于较早阶段；完整编辑语义、跨项目和高级调度仍需继续实现。

连续编辑后端又增加异步单 TU 预览、最新修订保护、取消、内存关系查询和可调结果预算，见 [异步预览报告](12-异步语义预览与修订一致性.md)。预览与磁盘索引合计最多一个编译进程；项目级 overlay 遮蔽/合并、preamble 复用和原生可编辑界面仍待实现。

**代码分析是 Symweft 的核心产品能力；低资源、快速分析和即时关系查询是核心质量要求。** 接下来围绕引擎与源码交互推进，通用 IDE 功能按这条主线补齐。图谱是分析结果的视图，不能先用演示节点替代分析能力。

引擎需要独立于平台 UI，同时深度参与 IDE 的文档生命周期。“独立”指可复用、可测试的代码边界，并不要求它只作为独立的离线扫描器运行。macOS 的当前实现是：Rust 分析库嵌入 Rust core 服务，Swift 原生前端通过本地管道访问。Linux/GNOME、Windows 和 CLI 复用同一个库与事实定义。

独立进程便于故障隔离、统计资源与按需回收；短消息的本地 IPC 不是主要分析成本。真正要避免的是每次光标移动启动进程、重新解析文件、遍历整个项目或同步等待全量索引。进程内 FFI 是否更合适，需在实际性能剖析后决定，不为省一次 IPC 复制整个分析器到 Swift。

### 优先级

1. **交互分析路径**：当前文件定义、调用点、作用域、关系查询、未保存内容的修订一致性。
2. **准确的语义关系**：绑定具体符号、定义/引用、出入调用、依赖与构建变体；明确不确定性。
3. **增量与成本**：复用解析、按依赖失效、受限并发、缓存淘汰、暂停/取消、实测回归。
4. **工作空间与跨项目**：持久化事实、反向关系索引、多个仓库与语言之间的证据连接。
5. **结果呈现与 IDE 扩展**：真实调用图/流程图/架构图、编辑事务、构建/调试；与前四项分阶段接入。

这里的优先级并不延后所有编辑能力：文档修订、输入反馈和未保存缓冲区本来就是交互引擎的一部分，需要早于完整的构建/调试系统完成。

## 2. 两条工作路径，一套事实模型

~~~text
原生编辑器 / 文件变更
        │ 文档 ID + 基准修订 + 编辑事务
        ▼
文档服务与调度器
        ├─ 交互路径：活动文档 → 增量语法 → 作用域/调用点 → 发布新修订
        │                         └─ 按需语义提供器 → 语义事实增量
        └─ 后台路径：工作空间变更 → 依赖失效 → 分批语义分析 → 持久化
                                                │
                    统一事实 / 证据 / 构建变体 / 快照
                                                │
                       查询层：源码、调用关系、架构、变更影响
~~~

交互与后台共享实体、关系、来源与版本定义，但有不同的数据寿命和工作预算。工作空间索引不能拦住当前文件的解析，重型语义分析不能拦住已经有结果的查询。

目标请求优先级：编辑与取消 > 光标上下文/跳转/已索引关系 > 打开的文档 > 可见项目的后台增量 > 全库首次索引 > 深度分析与报告。交互任务有截止时间；新修订到来时合并旧任务，停止计算已经无人需要的结果。

**当前服务仍是顺序 JSON Lines 调度。** 当前只承载受限的单文件分析，不在该循环中加入全量语义索引。接入全库工作前，必须先实现独立读取/调度、优先级队列、后台工作池、取消和结果订阅；不能把“用了异步 UI”误认为调度已经解决。

## 3. 分层精度与查询行为

| 层级 | 事实 | 典型用途 | 成本与边界 |
|---|---|---|---|
| A0 文本 | 内容、行索引、文件元信息 | 立即阅读、文件搜索 | 无需启动语言服务 |
| A1 语法 | 定义范围、词法作用域、显式调用点 | 大纲、当前函数结构、调用点定位 | Tree-sitter 增量语法；无法可靠绑定目标 |
| A2 语义 | 稳定符号、类型、引用、确定/候选调用边、导入依赖 | 准确跳转、谁调用我、跨文件关系 | 复用语言的编译环境和增量语义服务 |
| A3 深度 | CFG、数据流、可达性、架构规则、影响传播 | 复杂分析、报告与跨项目推理 | 按需计算，预算和分析假设独立显示 |

### 当前函数与调用关系

- 光标移动优先查询当前修订已有的范围/作用域索引；不因移动光标重解析。
- “调用点”是源码中的显式调用语法，可以立即显示和定位；“调用目标”需要语义绑定。
- “谁调用我”必须走被调符号的反向边索引，不能每次全库搜索同名文本。
- 缺少目标文件语义信息时，优先返回已有结果与覆盖范围，按需请求补齐；不在每次光标移动时触发深度分析。
- 大图采用有预算的邻居查询与展开，避免一次导出全项目关系后交给 UI 过滤。
- 架构聚合按持久化符号/模块 ID 计算；不得由 UI 从当前可见图反推全局依赖。

语法层的同名调用不会被直接连接为真实边。重载、方法接收者、trait/虚方法、宏展开、条件编译、Python 动态绑定、反射和回调都需要各自的语义证据或明确的候选状态。

## 4. 文档、快照与一致性

### 文档身份

正式模型使用 workspace/project/document 标识与规范化 URI，保留构建目标和变体。当前原型在一个 core 会话中以工作空间相对路径定位文档，不能将相同文件名当成相同文档。

### 修订事务

1. 打开文档，产生修订 R，返回该内容的 A1 快照。
2. 编辑请求携带 base_revision=R、UTF-8 字节范围与新文本。
3. 验证修订、范围和资源预算后解析。
4. 成功后一次性发布 R+1 的定义与调用点；失败保留 R，不暴露半更新快照。
5. 查询携带所需修订；旧修订请求返回 stale_revision，而不是悄悄查询新内容。
6. 前端收到迟到结果时按文档与修订丢弃；不得把旧文件的结构覆盖到新文件上。

当前修订是进程内单调递增的 token，不承诺连续 +1；切换工作空间清空缓存但不复用修订。重启 core 后前端必须重新建立会话并打开文档。后续增加明确的会话/工作空间 generation 与可持有的不可变快照，支持并发读和后台发布。

### 未保存内容

活动文档事实应来自编辑缓冲区，磁盘变化不能覆盖未保存内容。后续文档服务持有唯一权威缓冲区，处理外部修改、保存和冲突；工作空间查询将活动 overlay 叠加到持久化基线上。

当前 document.edit 仅验证内存分析事务，不写磁盘，macOS UI 仍只读。document.open 当前以磁盘内容为准并重新对齐该路径；在接入可编辑 UI 前，必须实现 dirty/版本所有权，避免再次打开覆盖未保存编辑。

### 坐标

core 使用零起点 UTF-8 字节偏移、半开范围；展示行号从 1 开始。AppKit 使用 UTF-16。前端以行锚点转换坐标，检查 emoji、组合字符与 CRLF；禁止直接把字节下标当成 NSRange。核心拒绝切入 UTF-8 字符中间的编辑和查询。

## 5. 增量分析策略

### 语法增量

- 每个热文档保留源码、语法树和紧凑的文件事实。
- 对编辑应用 Tree::edit，再使用旧树解析；整缓冲区重载通过 UTF-8 安全的公共前/后缀生成单次替换范围。
- 内容相同直接返回原修订，parse/extract 耗时为零。
- 不长期保留指向旧树的 Node；事实只保留范围、局部 ID、名称和证据。
- 当前实现复用语法树，但每次成功解析后仍遍历整个文件重新提取事实。不能把它宣传为“全链路按修改行增量”。下一步按定义/作用域缓存事实块，并处理下游偏移平移。
- changed_ranges 只反映语法结构变化，不足以捕获所有名称变化。将来跳过事实更新时，还必须考虑编辑文本范围、token/内容指纹及名字/导出变化。

### 语义增量

记录文件/模块之间的导入、声明依赖、实现依赖与构建配置依赖。函数体变化优先重算该函数的调用/数据流；对外签名、类型布局、宏、生成文件或构建配置变化才扩大失效范围。不能假设所有语言都能只重算一个函数，粒度由语义提供器保证。

使用两个内容指纹：源内容与对外可见语义摘要。源内容变化但公开摘要不变时，不默认重算所有依赖方。跨项目索引缓存键包含版本、目标、特性/编译参数与分析器版本，不能只按路径缓存。

C/C++ 保留头文件与编译变体、预处理和模板实例语义；Rust 保留 crate graph、features、cfg 和宏环境；Java 保留 classpath/module path 与源码级别；Python 保留解释器环境、导入路径和可选框架规则。运行构建脚本或插件需由对应工作空间的明确策略控制。

## 6. 低资源设计

### 当前已落地的边界

| 资源 | 默认约束 | 超限行为 |
|---|---|---|
| 热文档 | 8 个 | 淘汰最近未分析/重新打开的旧文档 |
| 热源码总量 | 4 MiB | 淘汰其他热文档 |
| 单文件交互分析 | 512 KiB | 保留最多 2 MiB 的文本阅读，提示分析预算 |
| 估算的缓存保留量 | 64 MiB | 淘汰其他热文档；单文件超限则拒绝发布 |
| 每文件定义与调用点 | 合计 20,000 | 拒绝本次分析，保留上一个成功修订 |
| 每文件语法遍历 | 200,000 节点 | 同上 |
| 一次解析与提取 | 200 ms 协作式截止时间 | 取消/拒绝发布，保留上一个成功修订 |

64 MiB 是源码、事实分配和节点数 × 96 字节的**估算记账**，并非精确的语法树分配量或 OS RSS 硬上限。Tree-sitter 内部池、grammar 映射、解析时的新旧树和源码副本、JSON 序列化、分配器与 UI 均不在这一数字内。截止时间也不是硬实时保证；回调以解析器检查频率生效，必须结合端到端实测。

当前只有一个复用的 Parser，不为每个文件创建语言服务。五种 grammar 随二进制提供；没有后台全库轮询、自动启动的 JVM、Python 解释器或编译器进程。

### 工作空间阶段的预算

- 打开的语义服务数量与语言/项目绑定，默认只激活当前任务需要的服务；闲置可退出，索引仍可查询。
- 限制并行解析进程、线程、内存估算与 CPU 时间；按电源状态、前台交互和系统压力收缩后台工作。
- 把冷文件压缩为可持久化事实与摘要，避免全库保留 AST、完整源码和重复字符串。
- 内部使用紧凑整数 ID 与名称驻留；跨 IPC 只传需要的切片。当前原型的字符串事实结构后续经剖析再压缩。
- 一条语义事实尽量复用一个权威来源，避免 IDE、调用图和架构图各自建立完整语义数据库。
- 持久化批量提交，前台输入先发布内存快照，避免每次按键 fsync。
- 无变更且无请求时停止分析任务；不设置永久索引轮询线程。文件监听事件需合并、去重和稳定性等待。
- RSS、峰值分配和缓存记账分别观测；释放缓存不代表分配器立即把所有内存归还 OS。

GPU 优先服务图谱绘制和原生合成。语义解析、依赖更新和索引查询先优化算法与数据布局；不为 GPU 卸载增加大规模数据复制。静态界面不应持续刷新占用 GPU。

## 7. 语义提供器与跨项目关系

共享引擎负责调度、事实/证据模型、版本、存储、查询和跨项目连接；语言提供器负责其擅长的类型与符号绑定。按需复用成熟的增量语义实现，避免在 Rust 中重写全部语言编译器，也避免“为每条边发送一次 LSP 请求”的高往返成本。

先打通一个语言的完整关系闭环并测量成本，再扩展：优先 Rust 自举和 C/C++ 编译数据库；Python、Java 随后复用其环境和语义提供器。具体集成方式可为服务协议、批量索引导入或专用 adapter。LSP 编辑能力与批量语义导出不是同一个接口，不能假定 callHierarchy 可以高效构建完整项目调用图。

A2 事实至少包含：稳定符号 ID、源位置、构建变体、定义/引用、调用位置、一个或多个目标、证据类别、提供器/规则版本、覆盖范围和 freshness。确定绑定、动态候选、外部声明、运行时观测各自保存，不用一个虚假的百分比替代语义。

持久化关系必须同时有 outgoing 和 incoming 索引。跨项目查询先识别同语言的包/库依赖，再通过显式 FFI、RPC/IDL、HTTP 路由或消息契约连接边界。名称相同不能作为跨项目调用证据。图的每条跨边界关系都能回到源码、契约或规则来源。

## 8. 当前实现与验收边界

### 已实现

- crates/symweft-analysis：共享 Rust 语法分析库，支持 Python、C、C++、Rust、Java grammar。
- 提取常见命名定义、匿名闭包作用域、显式调用/部分构造语法；Rust 宏调用作为独立 kind。
- 版本化快照、内存编辑、同内容复用、旧树增量解析、资源预算、缓存淘汰和查询。
- core 的 document.open / document.edit / document.close / analysis.get / analysis.at / analysis.stats。
- macOS 大纲、按光标所在函数筛选调用点、点击定位、引擎耗时；仍为只读阅读 UI。
- 所有调用点均为 evidence=syntax、resolution=unresolved；owner_id 表示语法体包含关系。

### 尚未实现

- 语义目标绑定、准确的跨文件入调用/引用、完整类型/变量符号表、持久化工作空间关系与跨项目图。
- 全量语义后台调度、请求级主动取消、并发快照、文档监听、自动编辑输入与安全保存。
- CFG/数据流与图形画布。控制流不能用调用语法列表代替。
- 当前 grammar 提取只覆盖已适配的节点类型；隐式构造/析构、运算符、反射、宏展开内容等不完整；.h 默认按 C 分析，后续需要语言/构建变体覆盖。
- 当前单文件 context 查询线性检查有上限的事实列表；后续根据测量改为区间和作用域索引。前端当前持有该文件快照，光标查询无 IPC。

### 后续实施门槛

1. **当前闭环**：多语言提取正确性、Unicode/修订、失败原子性、缓存限制与可复现延迟基线。
2. **交互引擎**：文档缓冲区所有权、编辑输入/外部变更、按作用域增量提取、并发快照和优先级调度。以持续输入时的响应为验收。
3. **语义闭环**：一个语言的定义/引用/出入调用可互相验证，支持未保存 overlay、环境变化与失效更新。
4. **工作空间引擎**：持久化与双向索引，热启动、增量失效、并行/电源预算，不以全量重扫完成每次更新。
5. **跨项目与图谱**：版本/构建变体、证据链、局部展开，图与源码同一查询快照。

## 9. 测量方法

基准必须分别记录：冷解析、无变化重开、单次编辑、事实提取、热上下文查询、IPC、端到端界面响应、RSS/峰值与空闲 CPU。不以 debug 构建或一次“平均耗时”作性能结论。

当前可重复命令：

~~~sh
cargo run --locked --offline --release -p symweft-analysis --example latency
~~~

该微基准为每种语言生成 400 个函数，分别执行 15 次冷分析、100 次增量改名、100 次无变化分析和 10,000 次上下文查询，报告 p50/p95。冷分析包含首次 Parser 设置，但不包含进程启动/磁盘读取；grammar 和 OS 页缓存可能已热。增量总耗时包含源码复制、旧树编辑、解析和全文件事实重提取。它不包含 Swift、IPC、语义引擎，也不能证明百万行仓库表现。

工作空间验收补充：固定开源仓库 commit、语言/编译环境、文件/行数/事实数量；分首次索引、持久化热启动、局部体修改、公开签名变化、头文件/配置变化测量。在低内存与 CPU 受限条件下验证降级，记录未完成/候选范围；用 profiler 确认热点后优化。

性能回归阈值需在固定机器和稳定样本后建立。总体设计中的理想性能预算仍是目标，不是本轮保证。
